# 管理ループ（/dev-pm）設計

> 共通の土台（なぜ多エージェントか・ロール定義・4ゲート思想・人間ゲートの位置）は `docs/dev-loop.md`。
> 企画フェーズは `docs/dev-plan.md`、実装フェーズは `docs/dev-build.md`。
> このドキュメントは **「承認済み提案を開発チームに渡して回収する管理ループ」** の設計。

---

## 1. 目的

企画（`/dev-plan`）と開発（`/dev-build`）の間に **PM（開発マネージャ）** を置く。

企画は「何を作るか」を決め、開発は「渡された1件を作り切る」。
その間に落ちていた仕事＝**「承認された複数の提案を、どの順で・どこで・何件ずつ流すか」**を PM が持つ。

これが無いと起きること（実際に起きていた）:

| 症状 | 原因 |
|---|---|
| メイン作業ツリーが実装で汚れる | 誰も作業場所を払い出していない |
| 別々の提案が同じファイルを踏んで片方の意図が消える | 衝突判断をする人がいない |
| 検証は緑なのに変更が反映されない | 別ツリーの dev サーバーを掴んでいた（ポートの持ち主がいない） |
| 落ちた提案が放置される | 回収して差し戻す人がいない |

## 2. スコープ

- **入力**：社長承認済みの `docs/plans/<id>/proposal.md`（複数）。
- **やる**：優先度判断・依存/衝突の検出・実行キュー編成・**build worktree の払い出し**（ブランチ／`npm ci`／専用ポート）・
  `/dev-build` の起動と結果回収・proposal のステータス管理・社長への報告。
- **やらない**：作る物の再選定（企画）、技術設計と実装（開発チーム）、proposal の書き換え。

## 3. 3ループの関係

```
[企画] /dev-plan   責任者が実プレイ→ proposal.md            ＠ 企画 worktree（plan-<日付>）
   ↓ 社長ゲート（承認 / 修正 / 却下）
[管理] /dev-pm     PM が優先度判断・衝突検出 → 実行キュー
                   → build worktree を払い出し（1提案=1本）
                   → /dev-build を1件ずつ起動 → 結果回収・差し戻し判断
   ↓
[開発] /dev-build  planner→engineer→qa→reviewer×3→PR       ＠ build worktree（build-<id>）
```

人間ゲートは**企画↔管理の1回（社長承認）だけ**。PM の優先度判断に承認ゲートは足さない（着手順は通知のみ）。
ただし **要社長判断（🔧）が未解決の提案は PM が止める**。

## 4. 作業場所の規約（worktree）

| 場所 | 用途 | ブランチ | ポート |
|---|---|---|---|
| リポジトリ直下 | 参照・PR マージ。**実装しない** | `main` | 5173 |
| `.claude/worktrees/plan-<日付>` | 企画（実プレイ・proposal 起票） | `worktree-plan-<日付>` | 5174-5179 |
| `.claude/worktrees/build-<id>` | 開発（1提案＝1 worktree＝1 PR） | `worktree-build-<id>` | 5180-5199 |

- build worktree は **`origin/main` から切る**（企画ブランチを土台にしない＝採用外の提案を PR に混ぜないため）。
- 承認された id の proposal だけを企画ブランチから取り込む：
  `git checkout $(git rev-list --all -1 -- docs/plans/<id>/proposal.md) -- docs/plans/<id>`
- **専用ポートを固定**する（`npm run dev -- --port <P> --strictPort` / `GAME_PORT=<P> npm run test:e2e`）。
  自動ずらし任せにすると、別ツリーの古いサーバーを掴んで「緑なのに変わっていない」偽グリーンが出る。
- 新しい worktree に node_modules は無い。払い出し時に `npm ci`。

## 5. 優先度判断の軸（pm エージェント）

`.claude/agents/pm.md`。読み取り専用で、実行キューを構造化して返す。

1. **効果** — 最上位の目的（継続＝広告収益）にどれだけ直接効くか。proposal の主張を実コードで軽く裏取りする。
2. **コスト** — 触るファイル数・新規 UI の有無・テストの重さ。
3. **リスク** — コアループ／経済バランスへの波及、後戻りのしにくさ。
4. **前提** — 依存（`dependsOn`）と**衝突**（`conflictsWith`：同じファイル・数値・画面）。

**衝突する提案は同じバッチに入れず前後に分ける。** 迷ったら衝突ありに倒す（並行で壊すコストの方が高い）。

## 6. 実行キューは直列

1件ずつ `/dev-build` を起動する。並列にしない理由:

- **Playwright は1本**しか掴めない（QA 同士が互いのブラウザを壊す）。
- 検証・審査は「落とす」のが仕事で、同時進行だと差し戻しの因果が混ざる。

並列化するなら worktree・ポート・ブラウザを完全に分離してからで、現状は PM が順序を決めることで代替する。

## 7. 回収（PM の本業）

| 結果 | 処置 |
|---|---|
| 通過・PR 作成 | proposal は `完了`（workflow がコミット済み）。PR URL と dev server URL を社長へ。worktree は**残す**（実機チェック用） |
| 検証 fail / 審査 approve<2 | proposal を `未完了` に戻す。**実装の問題**なら同 id を再投入（最大1回）、**提案の問題**なら企画へ差し戻し |
| 計画で blocked | 企画へ差し戻し。worktree は `git worktree remove` で片付ける |

バッチ終了時に、着手した全 id の結果と `defer` に残した提案の理由を社長に報告する。

## 8. proposal のステータス遷移（誰が動かすか）

`未完了 → 進行中 → 完了`（定義は `docs/dev-plan.md` §5）。

- `未完了` … `/dev-plan` が起票時に付与
- `進行中` … **PM** が build worktree へ取り込むときに更新
- `完了` … **開発ループ**が通過時の per-item コミットで更新
- 不通過で `未完了` に戻すのも **PM**
