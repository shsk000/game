# 開発ループ（/dev-build）設計

> 共通の土台（なぜ多エージェントか・ロール定義・4ゲート思想・人間ゲートの位置）は `docs/dev-loop.md`。
> 企画フェーズの規約は `docs/dev-plan.md`。このドキュメントは **「社長承認済みの提案を実装する開発ループ」** の設計。

---

## 1. 目的

社長が承認した提案（`docs/plans/<id>/proposal.md`）を入力に、**技術計画→実装→検証→審査→PR** を回す。設計の良し悪しは企画ループで社長が承認済みなので、開発ループは **「承認された物を、正しく・目的通りに作る」** ことに集中する。

## 2. スコープ

- **入力**：承認済み `docs/plans/<id>/proposal.md`（複数 id 可）。未承認の提案は流さない。
- **やる**：技術計画・実装・4点セット検証・敵対的審査3体・per-item コミット・PR 作成。
- **やらない**：作る物の再選定（それは企画ループ）。承認された狙いから外れる改変は審査で落とす。

## 3. ロールと流れ

`.claude/agents/` のロールを使う。1つの id につき縦に回す。

```
[企画/planner] proposal を技術計画 plan.md に落とす（approach・触るファイル・因果チェーン・CAP・testPlan）
   ↓
[実装/engineer] 最小変更＋unitテスト  ←──┐
   ↓                                    │ 検証NGは最大3回差し戻し
[検証/qa] 4点セット(build/unit/ui/e2e)＋実機入力 ─┘
   ↓ pass
[審査/reviewer ×3] 敵対レビュー多数決 → approve≥2?
   ↓ 通過＝この id の変更だけ即コミット / 不通過＝変更破棄
[統合] 通過コミットを push → PR作成（gh）→ ★dev server は起動したまま残す
```

- 人間ゲートは**挟まない**（企画↔開発の1回で承認済み）。品質は検証＋審査3体で担保。
- 技術計画（planner）の出力先は同じ `docs/plans/<id>/plan.md`。proposal と対で残る。

## 4. 技術計画テンプレート（`docs/plans/<id>/plan.md`）

proposal（プロダクト層）を実装レベルに落とす層。RFC/設計書寄り。

1. **目的1行** — proposal の狙いを実装者向けに1行で
2. **因果チェーン** — 変更が最終結果（funds/評価/解放/実績等）まで届く経路
3. **CAP 列挙** — 途中の上限/クランプ/係数。報酬がCAPに埋もれないか（アンチパターン#1対策）
4. **approach** — 最小変更の方針・採る/採らない選択と理由
5. **触るファイル**
6. **testPlan** — unit/ui/e2e のどの層で何を担保するか
7. **完成条件チェックリスト** — proposal の成功条件を検証可能な粒度で

## 5. 安全ガード

- **審査 approve<2 または 検証 fail の id は統合しない**（PR に混ぜない）。通過ゼロなら PR を作らない。
- **per-item コミット隔離**：通過 id は直後にその id の変更ファイルだけ個別コミット、不通過 id は作業ツリーを破棄（`git restore` ＋ その id が作った未追跡のみ削除。`git add -A`/`git clean` は使わない）。
- 実装は最小変更。proposal の狙いに紐づかない改変は審査で落とす。
- 機械検証不能な項目（音・体感・文言トーン）は検証者が `ownerCheck` ラベルで PR に残す。

## 6. PR 作成後：dev server を起動したまま残す

**社長は最終的にゲームで実機チェックする**ため、PR を作ったら **dev server を落とさず起動したまま**にし、社長が承認済み機能をブラウザで触れる状態でハンドオフする。サーバー起動・実機導線はメインセッション側で管理する（背景エージェントは Playwright/サーバー管理に不向き）。

## 7. 中断・fork からの復旧

Workflow は会話プロセス上で回るため、バックグラウンド fork で中断し得る。復旧手順（同一セッション `resumeFromRunId` 再開／fork時は破棄せず保護コミットして残りロールを独立 Agent で手回し／qa はメインセッション）は `docs/dev-loop.md` の該当節に従う。**うまく回らなかったら根本原因を特定して skill/workflow を直す**（自己改善ルール、同）。
