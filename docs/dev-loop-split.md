# dev-loop 分割設計：企画ループ / 開発ループ（提案・GO待ち）

> 位置づけ：`docs/dev-loop.md`（現行の5ロール一括ループ設計）の改訂提案。
> このファイルは社長（オーナー）レビュー用のドラフト。GO 後に `dev-loop.md` へ統合し、コマンド/ワークフローを実装する。

---

## 0. これは何 / なぜ分けるか

現行 dev-loop は 責任者→企画→実装→検証→審査→PR を**一気に自動化**し、人間ゲートは末尾（PR）だけ。

**問題（実測）**：A-1「復帰オフライン収益×2」が、*計画通り正しく動くのに、報酬窓を企画会議画面の奥に埋めてプレイヤーが気付けない* まま通過した。審査(reviewer)3体は「正しく動くか」は検証したが、「そもそもこの設計でいいか」を**実装前に止める人がいなかった**。

**対策**：「何を・どう作るか決める工程」と「承認済みを実装する工程」を分離し、境界に**社長（人間）の承認ゲート**を1回置く。社長がGOした提案だけが実装に流れる。

---

## 1. 2つのループ

```
┌ 企画ループ /dev-plan（責任者のみ・コード変更なし・PRなし）──────┐
│ 責任者が【実際にゲームを遊ぶ(主)＋コードで裏取り(従)】             │
│   → 次に作るべき差分を「軽量PRD」で提案                           │
│   → docs/dev-loop/<id>/proposal.md をコミット                     │
└──────────────┬───────────────────────────────────────────────────┘
               │ ★社長ゲート：承認 / 修正指示（再企画）/ 却下
               ▼ 承認された <id> だけ
┌ 開発ループ /dev-build <id>（承認済みPRDを実装）──────────────────┐
│ 企画(planner) → 実装 → 検証 → 審査×3 → コミット → PR              │
│   入力＝承認済み proposal.md。planner以降は従来どおり自動          │
└──────────────────────────────────────────────────────────────────┘
```

- **企画ループ＝責任者だけ**。「何を・なぜ・どこに」を決める（社長がPdMに諮るイメージ）。`count`（既定3）で**提案件数を設定可能** — 責任者は上位 `count` 件をランク付けで提案し、社長が実装するものを選ぶ。
- **人間＝社長**。企画ループの提案を最終承認する唯一のゲート。
- **開発ループ＝承認済みPRDの実装**。技術詳細（planner）と品質ゲート（検証・審査3体）はここ。**PR作成後も dev server は起動したまま残す** — 社長がブラウザ実機で最終チェックしてからマージするため（サーバーを落とさない）。

---

## 2. なぜ「遊ぶ主・コード従」か（企画ループの情報源）

| 情報源 | 得られるもの | 単独だと |
|---|---|---|
| **実機プレイ（主）** | 退屈・詰まる・分かりにくい・埋もれてる＝**プロダクト勘** | コードだけ＝A-1の失敗を繰り返す（体験の欠落を検知できない） |
| コード/spec（従） | 実現可能性・targetFiles・因果チェーン・CAP | 遊びだけ＝既存機能を知らず的外れ |

**制約と現実解**：
- Playwright は**背景サブエージェントだと詰まる**（ロック掃除に `rm` 権限が無く停止）→「遊ぶ」は**メインセッションで**実行する。
- ゲームは**時間律速**（放置しないと進まない）→ DEV「開発を即完了」等で早送りして中盤まで到達してから評価する。

## 3. 軽量PRD テンプレート（`docs/dev-loop/<id>/proposal.md`）

PRD をベースに、PR-FAQ の「体験を先に書く」規律を混ぜた軽量版。**③④が肝**（ここがあれば社長が承認前に「なぜPlanScreenの奥？」を弾ける）。

1. **タイトル / ID / 優先度**
2. **課題（Problem）** — 実際に遊んで気づいた事実。北極星（継続＝広告収益）に対するギャップ
3. **プレイヤー体験（Job Story）** — 「プレイヤーが〈状況〉のとき、〈動機〉で、〈成果〉を得る」＝**いつ・どこで・なぜ触れるか**
4. **提案（What）＋UI導線・置き場所** — 何を、どの画面のどこに出すか
5. **なぜ今／北極星リンク** — 継続・広告収益にどう効くか
6. **成功条件・指標** — 完成条件＋測れる指標
7. **スコープ外（Non-goals）**
8. **リスク／要社長判断** — 新テーマ・大投資・コアループ改変フラグ

> 開発ループの planner はこの proposal を受けて、実装レベルの技術計画（approach・触るファイル・因果チェーン・CAP＝RFC/設計書寄り）を別途 `plan.md` に出す。PRD（プロダクト層）と技術計画（実装層）は2層で持つ。

---

## 4. 副次効果（前に出た2件も同時に解決）

- **fork耐性**：各ループが短くなり、バックグラウンド fork で全再実行になる窓が小さくなる。
- **見える化＋計画の資料化**：`proposal.md`（と `plan.md`）がコミットで残るので、各ロールの決定が後から読めて、中断後の復元の土台にもなる。

---

## 5. 実装方針（GO 後）

- コマンド：`.claude/commands/dev-plan.md`（企画ループ）・`.claude/commands/dev-build.md`（開発ループ）。
- ワークフロー：`dev-loop.js` を「plan相当（責任者→proposal）」と「build相当（planner→実装→検証→審査→PR）」に分割（2ファイル or モード引数）。
- ロール：`producer` は**メインセッションで実機プレイ**する前提に更新（Playwright を使う手順を憲章に追記）。`planner` 以降は現行 `.claude/agents/` を流用。
- 現行 `dev-loop.md` の一括ループ設計は、この分割設計に置き換え／追記する。

## 6. 確定事項（社長決定 2026-07-25）

- **提案IDの採番**：`YYYYMMDD-<機能スラッグ>`（例 `20260725-offline-modal`）。
- **責任者が遊ぶ深さ**：DEV早送りで中盤到達、ブラウザ操作は目安20手・タイムボックスで打ち切り（溶かさない）。
- **planner の技術計画に人間ゲート**：無し（人間ゲートは企画↔開発の境界1回のみ）。
- **提案件数**：`count`（既定3）で設定可能。責任者は上位 `count` 件をランク付けで提案し、社長が実装対象を選ぶ。
- **開発ループの後始末**：**PR作成後も dev server を起動したまま残す**（社長がブラウザ実機で最終チェックしてからマージ）。サーバーを落とさない。この起動もメインセッション側で管理する（背景エージェントはPlaywright/サーバー管理に不向き）。
