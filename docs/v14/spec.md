## 0. この版で変えること（改訂背景）

### 現状の問題（オーナー指摘 2026-06-21）
> **「ゲーム作成のタイピングが壊滅的に面白くない」**

現状の開発体験は `src/features/develop/`（`useTyping.ts` / `DevelopScreen.tsx`）に集約されており、フローは
`office → plan(企画) → develop(開発タイピング) → release(発売)` の単線。開発は **1 枚の画面で「文字を打つ → 進捗バーが埋まる → 完了」だけ**。

北極星スキル（game-design §4「前向きな緊張」）が確定済みの装置（ノリゲージ＝倍率報酬 / ゴースト並走 / ポリッシュ＝方式 B / メタスコア開示の山場）が **1 つも実装されていない**うえに、**1 作の進行に起伏・変化・サプライズが無い**ことが「単調＝面白くない」の構造原因。

### この版の狙い
1 作の開発を **6 つのフェーズ**に分け、**フェーズごとに舞台（右パネルの大判イメージ）と空気が変わる**ようにする。さらに **各フェーズでランダムにイベントが発生**し、毎回違う展開・サプライズを生む。これで「単調なバー埋め」を「物語のある制作ドラマ」に変える。

> ⚠️ プロデューサー注（game-design §10）: 本版は **タイピングを主役**に保ったまま（卒業させない）、その周囲に**起伏とサプライズ**を足す方向。締切・イベント等で「誰も弾かない（§10-2）」を破らないよう、ハード失敗は入れない（§5-3・§10-Q2 参照）。

### この版でやること（柱）
1. **6 フェーズ制**（企画 / 開発 / テスト / デバッグ / 発売 / 開発完了）＝ §3
2. **フェーズ別の背景イメージ（右パネル）** ＝ §4
3. **フェーズ別ランダムイベント** ＝ §5
4. **3 カラム画面レイアウト**（モック準拠）＝ §6

## 3. フェーズ制

### 3-1. フェーズ定義と既存資産の対応

| # | フェーズ | 画像 | 既存の対応 | この版での扱い |
|---|---|---|---|---|
| 1 | 企画 | planning | `'plan'` screen（PlanScreen.tsx, 664行） | フェーズ 1 に位置づけ。ジャンル×テーマ×規模の選択 |
| 2 | 開発 | development | `'develop'`（useTyping/DevelopScreen） | 現行タイピングを中央パネルに。フェーズ 2 |
| 3 | テスト | testing | **無し（新規）** | プレイテスト。テストケース消化＋イベント入力ミッション |
| 4 | デバッグ | debugging | `develop` 内の `bugPhrase`（インライン） | **独立フェーズに昇格**。バグ修正タイピング |
| 5 | 発売 | release | `'release'` screen（ReleaseScreen.tsx, 622行） | フェーズ 5。売上監視 |
| 6 | 開発完了 | complete | **無し**（現状 release 後 office へ） | **新規**。打ち上げ＝結果サマリ／メタスコア開示の山場 |

### 3-2. フェーズ遷移（状態機械）
```
企画 →（開発開始）→ 開発 →（実装完了）→ テスト →（テスト完了）→ デバッグ →（バグ駆除完了）→ 発売 →（販売確定）→ 開発完了 →（打ち上げ閉じる）→ office へ戻る
```
- **実装方式（確定・オーナー了承）**：`current`（開発中プロジェクト）に `phase: DevPhase` を持たせ、**1 つのテイクオーバー画面の中央パネルだけをフェーズで差し替える**。`Screen` 型は据え置き（`develop` テイクオーバー内でフェーズ進行）。フェーズの保持は内部状態であり、プレイヤーへの提示は左の進行リスト＋右の画像（モック準拠・体験に影響なし）。
- `current` は非永続（リロードで消える）なので、`phase` 追加によるセーブ移行は不要。
- 各フェーズは **前フェーズの完了で解放**（左リストの 🔒 → ▶ → ✓）。

### 3-3. 各フェーズの中身（インタラクション・確定）
| フェーズ | 中央パネル（叩き台） | タイピング有無 |
|---|---|---|
| 企画 | ジャンル×テーマ×規模 選択（PlanScreen）＋ **「企画書を書く」ベース入力ミッション** ＋ 企画イベント | **有** |
| 開発 | 現行タイピング（実装 = コードを打つ） | **有（主役）** |
| テスト | テストケース消化＋イベント入力ミッション（§5-2 テスト表） | **有** |
| デバッグ | バグ修正タイピング＋イベント入力ミッション（§5-2 デバッグ表、現行 bugPhrase を発展） | **有** |
| 発売 | 売上監視（自動進行＋演出）＋イベント入力ミッション（§5-2 発売表） | 一部有（イベント時） |
| 開発完了 | 結果サマリ（総売上/レビュー/ファン/次回作ボーナス/会社評価）＋追加評価演出（§5-3） | 無（演出） |

> 北極星整合（確定）：イベントは全フェーズで **入力ミッション（タイピング）**で解決する（§5-0）ため、タイピングの主役性が全フェーズに行き渡る。発売・開発完了は基本演出だが、発売はイベント時のみ入力が入る。

### 3-4. 完成度・進捗の扱い
- モック右パネルに「現在の完成度 38%」がある。完成度は **フェーズ横断の通し進捗**として表示（企画 0% → 開発で伸びる → テスト/デバッグで品質確定 → 発売 100%）。
- 既存 `doneLoC / workTarget`（develop の進捗）をフェーズ別の重みに割り当てる 🔧。

## 5. ランダムイベントシステム

### 5-0. 基本モデル（確定・オーナー設計 2026-06-21）

**各フェーズに最低 1 回の「ベース入力ミッション」を置く（オーナー決定・案B）。**
- イベントが発生しない時でもフェーズを素通りさせず、必ず 1 回は打つ瞬間を作る（タイピング主役の徹底）。
- 例：企画＝「企画書を書く」、テスト＝「テストケースを確認する」、デバッグ＝「バグを洗い出す」等 🔧（各フェーズのベース文は実装時に確定）。
- 開発フェーズのベース＝既存の実装タイピング（workTarget まで）。

**各イベント＝入力ミッション（短いタイピング課題）で成功/失敗が決まる。**
- 発生 → 「入力ミッション例」の文を打つ → **打ち切れたら成功（プラス効果）／打ち切れない・ミス過多なら失敗（マイナス効果）** 🔧（成功判定の条件は §10-Q3 で確定）。
- これにより **イベントもタイピングで解決＝タイピング主役を維持**（北極星 §10-1）。
- 失敗にもペナルティはあるが **ハード失敗（詰み）にはしない**（§5-4）。最悪でも「開発期間 +1 週」「発売延期」程度の取り返せる損に留める。

### 5-1. イベントの 5 系統（分類・確定）
| 系統 | 例 | 主な影響軸 |
|---|---|---|
| **トラブル系** | バグ発生 / 炎上 / サーバー負荷 | バグ率・評判 |
| **チャンス系** | 天才のひらめき / 配信者紹介 | 品質・売上 |
| **スケジュール系** | 締切迫る / 発売延期危機 | 開発速度・期間 |
| **市場系** | トレンド発見 / ライバル出現 | 売上予測・話題性 |
| **品質系** | 操作性改善 / バランス調整 | 評価・レビュー |

### 5-2. フェーズ別イベント表（叩き台・オーナー提示）

> 影響軸（面白さ/期待度/売上予測/話題性/操作性/バランス/不満度/信頼度/炎上リスク 等）は **現状コードに非存在**。**新名称軸として `current` に新設**し、リリース時に既存パイプライン（品質→メタスコア→売上/ファン）へ合流させる（オーナー確定。詳細 §5-6）。下表の数値は叩き台 🔧。

**企画フェーズ**（品質より「面白さ・期待度・売上予測」に効く）
| イベント | 内容 | 入力ミッション例 | 成功時 | 失敗時 |
|---|---|---|---|---|
| 天才のひらめき | 面白いアイデア | アイデアを形にする | 面白さ +15 / 期待度 +10 | アイデア消失 |
| コンセプト迷走 | 方向性がブレる | 方向性を決め直す | 企画安定 / 品質 +5 | 開発期間 +1 週 |
| 市場トレンド発見 | 流行ジャンル発見 | トレンドを分析する | 売上予測 +15% | 変化なし |
| 予算見直し | 予算検討 | 予算を調整する | コスト -10% | 開発速度 -5% |
| ターゲット再設定 | 想定ユーザー見直し | ターゲットを決める | ファン増加率 +10% | 評判予測 -5 |

**開発フェーズ**（開発速度・品質・バグ率に直結）
| イベント | 内容 | 入力ミッション例 | 成功時 | 失敗時 |
|---|---|---|---|---|
| バグ発生 | 不具合発見 | バグを修正する | バグ率 -10% | バグ率 +15% |
| 締切迫る | スケジュール逼迫 | 急いで実装する | 開発速度 +30% | 品質 -5 |

| ライバル出現 | 他社が類似作発表 | 差別化を図る | 話題性 +15 | 売上予測 -10% |
| 仕様変更 | 必要機能が増える | 仕様を組み直す | 品質 +5 | 開発速度 -10% |

**テストフェーズ**（遊びやすさ・バランス・操作感）
| イベント | 内容 | 入力ミッション例 | 成功時 | 失敗時 |
|---|---|---|---|---|
| 操作性に違和感 | 操作しづらさ発見 | 操作感を調整する | 操作性 +10 | 評価 -5 |
| 難易度が高すぎる | 敵/ボスが強すぎ | 難易度を調整する | バランス +10 | 不満度 +10 |
| 隠しバグ発見 | 稀な不具合 | 再現手順を確認する | バグ率 -8 | バグ率 +8 |
| テスター大好評 | 好反応 | 面白さを伸ばす | 期待度 +15 | 変化なし |
| UI が分かりづらい | 説明が不親切 | UI を改善する | 品質 +6 | 評価 -3 |

**デバッグフェーズ**（最も緊急感＝赤系 UI・警告音・短めタイマー）
| イベント | 内容 | 入力ミッション例 | 成功時 | 失敗時 |
|---|---|---|---|---|
| 致命的バグ | 進行不能 | 致命的バグを修正する | バグ率 -20% | 発売延期 |
| クラッシュ多発 | 特定条件で落ちる | クラッシュを直す | 品質 +8 | 評判 -5 |
| セーブデータ破損 | セーブ問題 | セーブ処理を直す | 信頼度 +10 | 炎上リスク +15 |
| 原因不明の不具合 | 再現困難 | 原因を特定する | バグ率 -12% | 開発期間 +1 週 |
| 修正の連鎖 | 直すと別バグ | 修正内容を確認する | 品質 +5 | バグ率 +10 |

**発売フェーズ**（売上・評判・ファン数・SNS 反応）
| イベント | 内容 | 入力ミッション例 | 成功時 | 失敗時 |
|---|---|---|---|---|
| SNS で話題化 | 発売直後に拡散 | 話題を広げる | 売上 +20% | 変化なし |
| 配信者が紹介 | 人気配信者がプレイ | 宣伝を強化する | ファン数 +25% | 評価変化なし |

| サーバー負荷増加 | アクセス集中 | サーバーを増強する | 同時接続 +20% | 評判 -8 |

### 5-3. 開発完了フェーズ（ランダムイベントではなく結果演出・確定）
開発完了は **タイピングイベントではなく、結果サマリと追加評価で気持ちよく終わらせる**。
- 必ず出す結果：**総売上 / レビュー評価 / ファン増加 / 次回作ボーナス / 会社評価**
- フレーバー追加評価（抽選で一部発火、結果のみ・入力なし）：
  | イベント | 内容 | 結果 |
  |---|---|---|
  | 神ゲー認定 | レビュー高評価 | 評判 大幅 UP |
  | 初週売上好調 | 予想超え | 資金 大幅 UP |
  | ファンアート投稿 | ユーザーが盛り上げ | ファン数 UP |
  | 続編希望の声 | 続編を求める声 | 次回作ボーナス |
  | アワード受賞 | ゲーム賞受賞 | 会社評価 UP |

### 5-4. 発生ロジックと UI（確定 + 🔧）
- **フェーズごとに発生しうるイベントだけを下部バーに表示**（全 5 種を常時出さない＝オーナー指示）。表示はそのフェーズの候補と各発生率 %。
- 進行中に一定間隔で抽選。下部バー「イベント発生率 N%」「次のイベントは…?」予告ゲージで気配を演出。
- 既存 `triggerBugIfDue`（gameStore.ts:742、確率 0.15 で bugPhrase 発火）を **汎用イベントエンジンに一般化**し、フェーズ×イベント表を駆動する。
- 各イベントの発生率は 🔧（§10-Q3）。

### 5-5. 設計原則（北極星準拠・厳守）
- **どのイベントもハード失敗（詰み）にしない**（§10-2「誰も弾かない」）。失敗の最大ペナルティは「開発期間 +1 週 / 発売延期」等の取り返せる損。
- マイナスイベントの回避・軽減は **入力ミッション（タイピング）で対応**できる（主役性の維持）。
- 一部イベントは **リワード広告の自然な接点**（締切迫る＝クランチ加速、ライバル＝一時加速）に接続できる（§7）。

> ✅ **時間の扱い（確定・オーナー決定）**: モックの「残り時間 46.8 秒」カウントダウンは **採用しない**。時間は従来通り **開発期間（経過週、GlobalTicker が裏で進める）** で表現し、遅れ＝**完成までの期間が伸びるだけ**（資金の固定費がかさむ）。「締切迫る／致命的バグ＝発売延期」等スケジュール系イベントの失敗も、**開発期間 +N 週**として効く（ハード失敗にはしない）。入力ミッションに制限を付ける場合も「打鍵が止まると進まない」止まり（タイマーで弾かない）。

### 5-6. 新名称軸とリリース合流（確定・オーナー決定「新名称軸を追加」）
イベント効果は `current` 上の **新蓄積フィールド（初期 0、イベント成功/失敗で ±）** とし、リリース時（`releaseWork`）に既存パイプラインへ合流させる。既存 4 要素（charPower 0.5 / genreAffinity 0.25 / typingScore 0.15 / luck 0.1）は維持し、新軸は **加点/減点項**として足す。

| 系統 | 新軸（current 蓄積） | 合流先（リリース時） |
|---|---|---|
| 品質系 | `funFactor`(面白さ) / `usability`(操作性) / `balance`(バランス) | 最終品質 `quality` に加点（`computeQualityV10` 後の補正項） |
| 市場系 | `hype`(期待度) / `buzz`(話題性) / `salesForecast`(売上予測%) | `computeRevenue` の softBonus・初動 share・`fanDelta` |
| トラブル系 | `bugRate`(バグ率±) / `reputationRisk`(炎上リスク) | バグ罰（perf noBugs 系）＋リリース後 fans/売上の減衰 |
| スケジュール系 | `devWeeksDelta`(開発期間±週) / `costMod`(コスト) | 経過週へ加算（§5-5 の時間方針）・固定費/devCost |
| 信頼系 | `trust`(信頼度) | fans 微増・リピート（次回作初動） |

- **評判（炎上危機・クラッシュ等の「評判 ±」）**：v0.14 では **評判★ HUD を出さない**（②）ため、評判系効果は **fans / 売上減衰 / metascore 補正** に落として表現する（独立した評判スコア軸は作らない）。
- 各軸の合流重み・上限は `src/data/balance.ts` に集約（叩き台 🔧）。クランプして品質/売上が壊れないようにする。

## 9. 後方互換・データ移行

- **`current`（開発中プロジェクト）は元々永続化されない**（リロードで `null` に戻る／調査で確認）。よって `phase` や新軸フィールドの追加による **セーブ移行は不要**。

- 防御的に、`current` 読み出し時に `phase` 未設定なら `development` を既定とする（通常は発生しない）。
