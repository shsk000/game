# ゲームスコア計算の再設計（0から引き直す）

- **id**: `20260725-score-redesign`
- **優先度**: P0（コア体験。品質・売上の全経路に触る）
- **ステータス**: 計画（社長GO待ち）／**実装なし**
- **出典**: オーナー指摘「部分部分で言われても分からない。今の問題を解決する新しいスコア計算を0から決めたい」
- **最上位の目的**: **打った量と育てた社員が、そのまま作品の出来に出る**

---

## 1. なぜ引き直すのか（現状の破綻・実測）

| # | 問題 | 実測・根拠 |
|---|---|---|
| 1 | **1文も打たずに「ヒット」が出る** | 社員能力85・相性80で品質約72＝メタ70台。社員能力が打鍵と無関係に品質の60%を占めるため |
| 2 | **上手い人ほどイベント報酬が0になる** | 品質の加点枠は8点で、4つの数値とイベント報酬が共有。4つの数値だけで平均5点・速い人は8点に張り付く |
| 3 | **装備が「社員の能力」を上げていない** | 装備は4つの数値の寄与に掛かる別枠6点。社員には何も起きない |
| 4 | **デザイナーの効果が存在しない** | `sumDesignerBonus` が未接続。表示は「品質基礎 +5.0」（オフィス・企画画面の2箇所） |
| 5 | **社員の得意分野が存在しない** | `specialties` はガチャ演出の表示のみ。カテゴリ体系も6種で4つの数値とズレ |
| 6 | **4つの数値がプレイヤーに見えない** | 品質の5〜8点を決めているのに画面に一切出ない |
| 7 | **「運」が運になっていない** | 常に50点固定＝全員に配られる5点の下駄。名前だけ運 |
| 8 | **開発期間の効果が表示だけ** | イベント「開発期間 −1週」はカレンダーも固定費も動かさず、利益見込の表示だけ良くする |
| 9 | **4つの数値の重み差が意味を持たない** | プログラム0.12〜ゲームデザイン0.05（2.4倍差）なのに、チケットは4カテゴリ強制周回で選べない |

**共通の病理**：スコアへの経路が **並列に4本**（社員能力60% / 打鍵の成績15% / 加点枠A 8点 / 加点枠B 6点）あり、
互いに独立なので「何をすればスコアが上がるか」が繋がらない。上限の共有で報酬が消え、未接続で表示だけが残る。

---

## 2. 新設計の原則

1. **因果を一本にする** — `装備 → 社員の実効能力 → 打鍵で積む4つの数値 → 品質 → メタスコア → 売上`
2. **打たなければ品質は出ない** — タイピングゲームとして当然の前提を回復する
3. **表示した数値は表示どおり効く** — 上限の共有・未接続をゼロにする
4. **中間の概念を作らない** — 「面白さ」「売上予測」のような、プレイヤーに意味が伝わらない中間変数を置かない

---

## 3. 新しいスコア計算

### 3-1. 4つの数値（＝作品の出来高）

プレイヤーが見る名前：**プログラム / グラフィック / サウンド / ゲームデザイン**

**開発フェーズ**で作業チケットの文を1つ打ち切るごとに、そのチケットのカテゴリへ加算：

```
加算量 = 基礎値 × 打鍵評価 × 社員の実効能力(そのカテゴリ)

  基礎値       = 10 🔧
  打鍵評価     = 速度ランク(GOOD 1.0 / GREAT 1.2 / PERFECT 1.5) × コンボ倍率(現行のまま：10で1.5 / 30で2 / 100で3)
  社員の実効能力(カテゴリ) = Σ_参加社員 ( power × 得意分野倍率 × 装備倍率 )
```

**企画フェーズ**の打鍵は **ゲームデザイン** に加算（企画＝設計なので筋が通る）。**テスト/デバッグ**フェーズでは加算しない
（テストは発覚、デバッグは返済のフェーズ）。

### 3-2. 社員の実効能力

```
社員1人のカテゴリ別実効能力 = power × 得意分野倍率(カテゴリ) × 装備倍率(カテゴリ)

  power        = 現行のまま（0..1 正規化・レベル成長込み）
  得意分野倍率  = 得意なカテゴリは 1.3 🔧 / それ以外 1.0
  装備倍率      = その社員の3スロット（PC・チェア・小物）の categoryMul の積（現行データをそのまま使える）
```

- **得意分野**（今は死んでいる `specialties`）を**4つの数値と同じ4カテゴリに作り直して**接続する（問題5を解決）
- **装備は社員に掛かる**（問題3を解決）。カテゴリ別の効き方は現行データを維持＝PCはプログラム、液タブはグラフィック
- **役割（プログラマー/デザイナー/広報）は開発の担当分けには使わない**。得意分野が担当を表す
  - 広報は従来どおり売上ボーナス専用
  - デザイナーの「品質基礎 +○」は**廃止**し、表示も消す（問題4を解決。役割ではなく得意分野が品質を決める）

### 3-3. 品質

```
出来高 = プログラム + グラフィック + サウンド + ゲームデザイン      ← 重みは均等（問題9を解決）

基礎品質 = min(100, 出来高 / 規模の基準出来高 × 100)
           規模の基準出来高 = ミニ 400 / スマホ 1000 / インディー 2500 / 話題作 6000 / AAA 15000 🔧

品質 = clamp(0..100, 基礎品質 × 相性係数 − 残バグ × 2 )

  相性係数 = 0.8 〜 1.2（ジャンル×テーマ相性 0.7〜2.0 を線形写像）🔧
```

**これで消えるもの**：
- 加点枠A（`AXIS_QUALITY_BONUS_CAP` 8点）／加点枠B（`EQUIP_QUALITY_BONUS_CAP` 6点）／`STAT_QUALITY_BONUS_CAP`
  → 正規化（出来高 ÷ 基準）が自然な上限になるので、共有CAPが不要（問題2を解決）
- 社員能力スコア（`charPower`）の60%重み → **1文あたりの倍率に転生**（問題1を解決）
- 品質ウェイト（`QUALITY_WEIGHTS` 0.60/0.15/0.15/0.10）
- 打鍵の成績（WPM・コンボ・精度）の15%枠 → **打鍵評価として4つの数値に吸収**（経路の二重化を解消）
- 「運」の固定50点 → **廃止**（問題7を解決。ブレは 3-4 の評価家ブレ ±5 に一本化）

**精度（ミス）の扱い**：現行どおりミス打鍵はバグになり、残バグ1匹＝品質 −2。精度は別枠で減点しない（二重罰を避ける）。

### 3-4. メタスコア（現行維持）

```
メタスコア = round(clamp(0..100, 品質 + トレンド合致(両方+10 / 片方+5) + 評価家ブレ(−5〜+5) ))
```

### 3-5. 売上（現行維持）

```
売上総額 = baseRevenue[規模] × 段倍率(メタスコア)
         × (1 + 広報PR) × (1 + ファン) × (1 + 初回組合せ)
         × 話題性補正 × マーケ広告 × トレンド売上倍率
初動 = 20% 即入金 / 販売プール = 80% 時間減衰
ローンチ広告 = 初動 ×1.5（表示は「初動売上 +50%」）
```

段倍率（0〜29 ×0.33 / 30〜49 ×3.33 / 50〜69 ×10 / 70〜79 ×33 / 80〜89 ×100 / 90〜94 ×250 / 95〜100 ×500）は現行維持。
**ただし品質の作り方が変わるのでメタスコアの分布が変わる** → §6 の再チューニングが必須。

## 4. イベントの作り直し（軸を廃止して効き先を直接書く）

**発生**：企画フェーズ完了時（企画→開発の遷移）に1回だけ抽選。**毎回は出ない**。

**表示**：モーダル。**打鍵なし**。読んで閉じたら効果確定。

**発生率と内容がゲーム状態で変わる**（固定確率をやめる）：
- 参加社員の能力合計
- ファン数
- トレンド合致（作っているジャンル/テーマが流行と一致しているか）

**報酬は中間軸をやめて効き先を直接書く**（面白さ/操作性/バランス/売上予測/開発期間は廃止）：

| 報酬の書き方 | 例 |
|---|---|
| 4つの数値に加算 | グラフィック **+40** |
| ファン | ファン **+30** |
| 売上 | 売上 **+10%** |
| 開発費 | 開発費 **−10%** |
| バグ | バグ **−3匹** |

**残す軸**（効いていることを実測済み）：話題性（売上＋ファン）／期待度（ファン）／信頼度（ファン）／炎上リスク（売上−・ファン−）
→ ただし**イベント表示では「ファン +30」「売上 +10%」と書き、軸名は画面に出さない**。

**廃止**：面白さ・操作性・バランス（CAPで死んでいた）／開発期間（表示だけの嘘・問題8）
**既存の8秒抽選イベント**：企画フェーズぶんは廃止してモーダルに一本化。開発フェーズぶんは残す 🔧（要判断）

## 6. 壊れるので作り直しが必要なもの（正直に）

1. **メタスコアの想定分布（`SCORE_TIERS`）とバランス全部**
   「約55%が赤字」「序盤はメタ70に届かない」は現行式の上に乗っている。新式では
   `progressionSimulation` / `solvencySimulation` / `balanceSimulation` を作り直して再チューニングが必要。
   **§3 の 🔧 の数値（基礎値10・基準出来高・得意分野倍率1.3・相性係数レンジ）は全部シミュレーション後に確定。**
2. **セーブ移行**：社員の `specialties` を6カテゴリ体系から4カテゴリへ変換する移行が必要（`storage.ts`）。
   `axes` は保存されないので移行不要。
3. **進捗（完成度）と出来高の関係**：進捗も打鍵で進むため、速く打つと早く終わって出来高が積めない。
   「速く終わらせる＝固定費が安い」vs「丁寧に積む＝品質が高い」というトレードオフになる。
   これは狙って良い設計だが、**進捗の伸び方（`progressGain`）との比率調整が必要** 🔧
4. **既存テストの大規模な書き換え**：`release.test.ts` / `metascore.test.ts` / 各シミュレーションテスト
