# アーキテクチャ設計資料 — ロジックとUIの分離（2026-07-09）

> **位置づけ**: エンジニアリング資料（ゲーム仕様は `docs/vNN/spec.md`）。テストの書き方は `docs/testing.md`。
> 実装時に守る規則の要約はスキル `.claude/skills/logic-architecture/`。移行の進捗は `tasks/todo.md`（P0〜P7）。

---

## 1. 何が問題か

いまテストが書けないのは、**「ゲームのルール計算」と「画面・保存・タイマー」が同じ場所に書かれている**から。

具体例：`releaseWork`（作品リリース時の処理、`state/gameStore.ts` 内 約180行）

```
いまの releaseWork の中身（1つのアクションに全部入り）：
  品質を計算 → Math.random() で揺らす → メタスコア算出 → 売上計算
  → ファン増減 → ジャンル解放判定 → 実績判定 → set() で反映
```

これをテストしようとすると：

- 計算部分だけ取り出せない（store のアクションに埋まっている）
- `Math.random()` 直呼びなので**同じ操作でも毎回結果が違う**。「売上は◯◯円になるはず」と書けない
- そもそも gameStore.ts を import しただけでセーブ読込と 5 秒毎の自動保存タイマーが動き出す

同じ問題が月次決算（`monthlyTick`）、採用候補生成、タイピング判定（useTyping）、DevelopScreen のゲームループにもある。

## 2. 設計のゴール：このプロジェクトで何を守りたいのか

構成を決める前に、「このゲームでテストに何を期待するか」を整理した。ここが判断の土台になっている。

**(a) 一番守りたいのはルール計算（経済・スコア・解放）である。**
このゲームの核は「品質→メタスコア→売上→ファン→解放」の数値パイプラインで、バランス調整（`data/balance.ts`）を今後も頻繁に繰り返す。調整のたびに「借金→ゲームオーバーの流れが壊れていないか」「解放条件が繰り上がっていないか」を手で確認するのは既に限界で、**回帰を機械的に検知できること**が最大の価値。

**(b) UI は頻繁に捨てて作り替える。**
v0.8→v0.15 の歴史で、開発画面・企画画面は何度も丸ごと作り直している（レーン案の不採用、チケット制への刷新など）。つまり**UI の細部に密結合したテストは書いても資産にならない**。UI テストは「ユーザー操作のシナリオが通るか」の粒度に留め、量も絞るべき。

**(c) 実装者は主に AI（Claude）である。**
規約が複雑だと守られない。人間がレビューで拾う前提も置けない。だから**ルールは少数・機械的・違反が見た目で分かる**ものにする必要がある。「この型の関数はこのディレクトリ」「乱数は引数で受ける」のような、コードを見れば守れているか即判定できる形が望ましい。

**(d) 動いているゲームを壊さないこと。**
約14,200行が現に動いていて、プレイ感の調整が主戦場。テストのための改修でセーブデータやゲーム体験を壊すのは本末転倒。**既存コードの変更量を最小にし、段階ごとに動作確認できる**移行手順が必須。

この4つを評価軸として選択肢を比較した。

## 3. 検討した選択肢

### 案A：構造は変えず、テストを増やす（E2E 増強）

いまの Playwright e2e を拡充して品質を担保する案。改修リスクはゼロ。

**不採用の理由**：(a) が満たせない。売上計算の境界値（倍率クランプ 0.5〜2.0、ファン下限 0 など）を e2e で検証するには「実際にゲームを最後までプレイする」操作が毎回必要で、1ケース数十秒×乱数のブレで、バランス調整のたびに回す回帰テストにならない。現に既存 13 本の e2e はスクショ確認が主で、数値ロジックの検証はできていない。

### 案B：ヘキサゴナル/クリーンアーキテクチャへの全面移行

外部との接点（保存・音・広告・乱数・時刻・UI）をすべてインターフェース（ポート）として定義し、ドメイン層が一切の実装詳細を知らない構成。テスタビリティの教科書的な到達点。

**不採用の理由**：このゲームの「外部依存」を数えると、本当に非決定性を持ち込むのは**乱数と時刻の2つだけ**だった。localStorage は同期APIでテスト時に丸ごと差し替え可能（`vi.stubGlobal`）、音は検証対象外、ネットワークは存在しない。つまりポートを6個切っても、テストが楽になるのは2個分で、残りは「書き換えるだけの工事」になる。(d) 変更量最小に反し、(c) ルールも複雑化する。**効果が出る2箇所だけポート化すれば、教科書構成の利点の大半が手に入る**というのがこの設計の中心的な判断。

### 案C（採用）：計算の切り出し + 乱数/時刻だけ注入

ルール計算を「入力→出力だけの普通の関数」に切り出し（§4）、乱数と時刻だけ引数で差し替え可能にする。store・React・保存の構造は変えない。

- (a) ルール計算が普通の関数になるので、境界値テストが1ケース数ミリ秒で書ける
- (b) UI テストは「シナリオが通るか」の粒度で別層に分離（`docs/testing.md`）
- (c) ルールは実質2つ：「計算は core/ か純関数に」「乱数・時刻は引数で」。違反はコードを見れば分かる
- (d) 呼び出し側の書き換えがほぼゼロ（後述のデフォルト引数方式）。移行は8段階に分割し、各段階で既存 e2e を安全網にする

### 案D：状態機械ライブラリ（XState 等）の導入

フェーズ遷移（企画→開発→…→リリース）を状態機械として宣言する案。遷移の網羅テストが書きやすくなる。

**不採用の理由**：現状のフェーズ遷移は `DEV_PHASE_ORDER` 配列の直線進行で、分岐がない。ライブラリの学習・依存コスト（(c)(d)）に対して得るものがない。遷移が複雑化したら再検討する。

## 4. どう直すか：「計算」と「実行」を分ける

案Cの中身。**ルールの計算を「入力→出力だけの普通の関数」として切り出し、store や画面は「計算結果を反映するだけ」にする。**

> 用語メモ：「同じ入力なら必ず同じ結果を返し、画面・保存・時計・乱数など外の世界に触らない関数」を**純粋関数**と呼ぶ。

### Before / After（releaseWork の例）

```ts
// ── Before：store のアクション内に計算が全部（テスト不能） ──
releaseWork: (opts) => {
  // …180行の計算。途中で Math.random() と Date.now() を直呼び…
  set({ funds, fans, library, ... });
},

// ── After：計算は core/release.ts の関数へ（テスト可能） ──
// 「いまの状態」と「乱数・時計」を引数で受け取り、「作品と変更分」を返すだけ
export const computeRelease = (ctx, opts, deps) => {
  // …180行の計算はここへそのまま引っ越し。乱数は deps.rng() を使う…
  return { work, patch };  // patch = 状態の変更分
};

// store 側は3行になる（計算しない。結果を反映するだけ）
releaseWork: (opts) => {
  const r = computeRelease(get(), opts, defaultDeps);
  set(r.patch);
  return r.work;
},
```

テストはこう書ける：

```ts
// 乱数に固定値を渡すので、結果は毎回同じ。普通の関数として assert できる
const r = computeRelease(状態のサンプル, undefined, { rng: () => 0.5, now: () => 0 });
expect(r.patch.funds).toBe(8_500_000);
```

## 5. 個別の設計判断とその理由

### 5-1. 乱数・時刻は「末尾デフォルト引数」で受け取る

```ts
// Before
const luck = 0.97 + Math.random() * 0.06;

// After（呼び出し側は今までどおり。テストの時だけ rng を渡す）
export const computeRevenue = (args, rng: Rng = Math.random) => {
  const luck = 0.97 + rng() * 0.06;
  ...
};
```

**考え**：注入の実現方法は (i) DI コンテナ、(ii) 関数のカリー化やファクトリ、(iii) デフォルト引数、の選択肢がある。(iii) を選んだのは、**既存の呼び出し箇所（metascore だけで十数箇所）を1行も変えずに済み**、テスト側だけが追加引数を渡せるから。(i)(ii) は呼び出し側全部の書き換えが必要で (d) に反する。デメリットは「引数を渡し忘れても型エラーにならない（本番乱数のまま動く）」ことだが、本番動作としてはそれが正しい挙動なので実害がない。

型は2つだけ（`src/core/ports.ts`）：

```ts
export type Rng = () => number;   // 0〜1 の乱数。テストでは固定値や seed 付き乱数（mulberry32）を渡す
export type Clock = () => number; // 現在時刻 ms。テストでは固定時刻を渡す
```

### 5-2. import 時副作用は `bootGameStore()` に集約する

gameStore.ts は現在、import した瞬間に「セーブ読込 → オフライン収益計算 → 自動保存タイマー起動 → `window.__gs` 設定」まで走る。これを起動関数 `bootGameStore()`（`state/boot.ts`）に集め、`main.tsx` だけが呼ぶ。

**考え**：「テスト時だけ副作用をスキップする if 文」を store 内に散らす案もあるが、環境判定の条件分岐は漏れやすく、本番とテストで別コードパスになる。**「起動処理」という概念を1つの関数にする**方が、本番もテストも同じコードで、テストは「呼ばない」だけで済む。ついでに e2e の決定化（`?seed=NN` で乱数を seed 固定にする配線）も起動処理として自然に置ける。

### 5-3. store はシングルトンのまま（ファクトリ化しない）

テスト向けの教科書的な構成は `createGameStore(deps)` でテストごとに store を作る形。

**考え**：調べたところ `useGameStore` の import 元は12ファイルあり、ファクトリ化はその全部+Provider 配線の書き換えになる。得られるのは「テストごとに独立した store」だが、同じことは**シングルトンを初期状態にリセットするヘルパー（`resetStore()`）**で実現でき、Vitest はテストファイルごとにプロセスを分離するので汚染も起きない。12ファイルの書き換えリスク > リセット方式の理論的な粗、と判断した。将来「複数セーブスロット」等で store の多重化が本当に必要になったら、その時にファクトリ化する。

### 5-3b. store は分割しない（1,010行問題の正体はロジック混入）

「gameStore が大きい」問題は切り分けが必要。**状態そのものは約20フィールド**（資金・ファン・ライブラリ・解放状況…＝セーブデータの形）で大きくない。1,010行あるのは releaseWork（180行）や monthlyTick 等の**計算がアクション本体に書かれているから**で、これは P3 の core 抽出で解消する（抽出後は「状態定義＋薄い配線」で概ね300行前後の見込み）。

そのうえで「複数 store への分割（useEconomyStore / useProjectStore…）」は**しない**：

- `releaseWork` は資金・ファン・ライブラリ・解放・実績・レコード・トレンドを**1回の遷移で同時に**更新する。store を分けるとこの原子性が失われ、store をまたぐ更新の手動オーケストレーション（片方だけ更新される不整合の余地）が生まれる
- セーブ/ロードは全状態のスナップショット。分割すると persist 配線が store の数だけ増える
- このゲームの状態は相互依存が強く（資金→ゲームオーバー、リリース→解放）、どこで切っても嘘の境界になる

**段階基準**：P3 完了後もファイルが肥大し続ける場合（目安：配線だけで500行超）、**slices パターン**で対応する。economy / project / progression のスライスを別ファイルに書き、1つの `create()` で合成する方式。store は1個のまま（原子性・persist は保たれる）で、ファイルだけが分かれる。

### 5-4. core の関数は「変更分（patch）」を返す

`computeRelease` は新しい状態全体ではなく `Partial<GameState>`（変わったフィールドだけ）を返し、store 側が `set(patch)` する。

**考え**：状態全体を返す形だと「計算関数が触っていないフィールドまで上書きする」事故（並行する tick との競合）が起きうる。patch 方式なら**関数が何を変えるのかがシグネチャと返り値で読める**うえ、テストで「変わるべきフィールドだけ変わった」ことを assert しやすい。

### 5-5. UI の計算切り出しは「3行」を目安にする

画面コンポーネント内の派生計算が3行を超えたら、同ディレクトリの `.ts` に純粋関数として切り出す（前例：`devImpact.ts`）。

**考え**：「全部切り出せ」は現実に守られない（JSX 内の三項演算子まで対象になる）。「複雑になったら」は判定できない。**行数の機械的な目安**なら (c) AI 実装者でも迷わない。3行は「クランプ1個＋分岐1個」程度で、それを超える計算はゲームルールである可能性が高い、という経験則。

### 5-6. DevelopScreen（2,101行）は今回リライトしない

**考え**：ここが今回最大の「やらない」判断。DevelopScreen はゲームループ・イベント抽選・演出が混在した最大の問題児だが、(b) の通り開発画面は v15 系で仕様が動いている真っ最中で、いま構造化しても次の企画変更で捨てる可能性が高い。かつ全面リライトは (d) のリスクが最大。今回は**打鍵判定（typingEngine）とイベント抽選の乱数だけ**を切り出し、画面全体の検証はユースケーステストと e2e に委ねる。v15 の仕様が固まったタイミングが本格的な分割の適時。

## 6. 置き場所のルール

```
src/
  core/          ← ★新設：複数の状態をまたぐルール計算（純粋関数のみ）
    ports.ts        Rng / Clock 型、mulberry32（seed付き乱数）
    release.ts      リリースパイプライン（computeRelease）
    economy.ts      月次決算・オフライン収益・借入返済
    progression.ts  ジャンル解放・実績判定
  utils/         ← 単機能の計算（metascore, sales, profit…）。今のまま（既にほぼ純粋）
  data/          ← 静的テーブルと調整値（balance.ts に数値集約）。今のまま
  state/
    gameStore.ts    唯一の store。アクションは core/ を呼ぶ薄い配線
    boot.ts      ← ★新設：起動時副作用の唯一の入口
    testing.ts   ← ★新設：テスト用の状態注入ヘルパー resetStore()
  features/      ← 画面。ルール計算を持たない（必要なら同 dir の .ts に切り出す）
    develop/typingEngine.ts ← ★新設：打鍵→コンボ/WPM/正確度の計算
  components/    ← 再利用 UI。GlobalTicker だけが実時間タイマーを持つ
```

**新しいコードをどこに書くかの判定**：

| 書こうとしているもの | 置き場所 |
|---|---|
| 複数の状態（資金・ファン・ライブラリ…）をまたぐ遷移 | `core/` |
| 入力→出力が閉じた単機能の計算 | `utils/` か feature 併設の `.ts` |
| ゲームバランスの数値・テーブル | `data/balance.ts` |
| 画面の見た目・入力ハンドリング | `features/` `components/`（計算3行超は切り出し） |

## 7. 段階移行計画

| フェーズ | 内容 | リスク |
|---|---|---|
| P0 | Vitest 基盤 + 既存純粋関数の単体テスト（プロダクション改修ゼロ） | なし |
| P1 | `core/ports.ts` + 乱数/時刻の引数化（metascore・採用・トレンド・抽選系） | 低 |
| P2 | gameStore の import 時副作用6箇所を `boot.ts` へ移動 | **高**（セーブ/復元。全e2e+手動確認で担保） |
| P3 | core 抽出：progression → economy → release（ロジック無変更の引っ越し） | 中（seed 固定で移植前後を比較） |
| P4 | typingEngine 抽出（useTyping は入力の受け口だけ残す） | 低 |
| P5 | 画面のユースケーステスト | 低 |
| P6 | Playwright 整理（ジャーニー3本に絞り、旧 spec は tests/archive/ へ） | 低 |
| P7 | ドキュメント・スキル最終化 | なし |

順序の考え：**リスクゼロの P0 で回帰検知の土台を先に作り**、以降の改修は常に「前フェーズまでのテスト+既存 e2e」を安全網にして進める。P2 を早い段階に置くのは、これが終わらないと store 絡みのテストが一切書けず、P3 以降の移植検証が手薄になるから。

## 8. この構成が保証すること

- どのテストも、import しただけでは何も起きず、同じ入力で毎回同じ結果になる
- `useGameStore` を使う12ファイルの既存コードは書き換え不要（公開APIは不変）
- e2e が使う `window.__gs` は boot 経由で維持される
- バランス調整は今までどおり `data/balance.ts` だけ触れば完結する
