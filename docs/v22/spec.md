## 0. 前提・課題認識（現状実装の確認済み事実）

本版の設計は以下のコード上の事実に乗せる（調査日 2026-07-19。行番号は当時の main。
実装時は v21 マージ後のコードで再確認する）。

| 項目 | 現状 |
|---|---|
| 候補生成 | `newCandidate()`（`src/data/employees.ts`）。basePower は `CANDIDATE_POWER_RANGE`＝**0.2〜0.6 の一様乱数**。ランクの概念なし |
| specialty | primary 1つ（ボーナス3〜10）＋40%で2つ目（1〜4） |
| 採用コスト | 候補の初月給 `wage` を即時徴収＋以後毎月給与。`wage = ¥30万 + power×¥60万 + (level−1)×¥5万` |
| 候補リフレッシュ | `REFRESH_COST`＝**¥50**（実質無料。v21 spec §5 で「統合判断は v22 で」と先送り済み） |
| 採用UI | OfficeScreen の採用モーダル。静的テキストのみ、演出なし |
| charPower | `computeCharacterScore()`：powerSum/規模別CAP×70（上限70）＋役割多様性（最大10）。**score 上限100・規模別 POWER_CAP が天井** |
| 分布ガード | `src/core/balanceSimulation.test.ts`：序盤70+＝0%／中盤80+＝0%／95+は終盤のみ（≤15%） |
| 進行ガード | `src/core/progressionSimulation.test.ts`：mobile解放8〜16作目・aaa到達25〜60作目・60作でLv7+ |
| 採用上限 | 12人（ワークステーション数と連動） |

**課題（roadmap 原文）**：採用は「候補を見る→雇う」の作業で、引きの快感がない。候補の能力差
（0.2〜0.6）はあるのに、ランク・希少性・演出として体験化されていない。

## 1. 事業目的と前提

北極星（game-design スキル）：広告収益・広告は人質にしない・長く遊ぶ人が一番得する・課金なし。

本版が解く問い（roadmap 原文）：**「採用を『作業』から『引きの快感』にできるか？」**

- ガチャは**ゲーム内資金のみ**で引く。リアルマネー・広告視聴の強制は一切絡めない
  （広告連動の無料ガチャは v0.24 の広告本実装まで保留。§5）。
- メタ進行3本柱のうち「会社が育つ（経営）」の採用体験を、評価開示（メタスコアガチャ）と
  同型の「開ける瞬間の快感」に揃える。

---

## 2. コンセプト

**この版で変えたこと**：採用フローを「候補1名提示＋¥50リフレッシュ」から「**資金を払って引く
社員ガチャ**」に置き換える。能力の抽選レンジ・成長・給与・charPower の各パイプラインは
**一切変更しない**。変えるのは「候補がどう生成され、どう提示されるか」だけ。

v21 で確立した設計原則を継承する：
- **新しい数値経路（ボーナス種別）を増やさない**。ランクは basePower 帯と specialty 構成の
  **ラベル**であり、ランク自体が品質・売上に加点する経路は作らない。
  → roadmap の「S＋固有ボーナス?」は**採用しない**（CAP罠の回避。差は basePower/specialty のみ）。
- **打鍵フローに介入しない**。ガチャは OfficeScreen（採用モーダル）内で完結する。

---

## 3. コアループへの影響

企画→開発→デバッグ→リリース→販売のループは無変更。採用の入口だけが変わる：

```
旧: 採用モーダル → 候補1名を見る →（¥50で引き直し）→ 初月給を払って雇用
新: 採用モーダル → ガチャ料を払って引く → カード開封演出（ランク開示）
     → 雇う（初月給を払う）or 見送る（候補は消える）
```

- **引き＝候補カードの排出**であり、自動雇用しない。雇用判断（初月給＋毎月給与の負担）は
  従来どおりプレイヤーに残す（B連発で枠が埋まる事故を防ぐ）。
- 見送った候補は保持しない（在庫UIを作らない。もう一度引くには再度ガチャ料）。

## 4. 経済設計

### 4-A. ランクと排出率 🔧（叩き台・roadmap 原文ベース）

| ランク | 排出率 🔧 | basePower 帯 🔧 | specialty 🔧 |
|---|---|---|---|
| B | 70% | 0.20〜0.40 | primary 1つ（ボーナス3〜7）。2つ目なし |
| A | 25% | 0.40〜0.55 | primary 1つ（5〜10）＋40%で2つ目（1〜4）＝現行相当 |
| S | 5% | 0.55〜0.70 | **2つ確定**（primary 6〜10＋2つ目 3〜6） |

- 帯内は一様乱数（現行 `rollPower()` の丸め・仕組みを流用し、レンジだけランクで切り替える）。
- 役職（programmer/designer/pr）の抽選 `ROLE_DICE` は現行のまま（ランクと独立）。
- **期待値の変化**：現行一様 0.2〜0.6 の平均 0.40 → 新方式の平均 ≒ 0.36。平均をやや下げ
  分散を上げる（＝引きの上振れが体験として立つ）。進行への影響は §8 のシミュレーションで検証。
- **S の上限 0.7 は現行上限 0.6 より高い**。ただし charPower は規模別 POWER_CAP と
  powerBonus 上限70で天井が固定されており、S は「天井に早く到達する」だけで天井を上げない
  （roadmap の判断ゲート「S でも Lv1 なら charPower 上限は変わらない」を構造で満たす）。

### 4-B. 価格 🔧（叩き台・規模スケール制）

- **単発価格は解放済み最高規模に連動**させる（賃料 `monthlyRent` と同じ参照方式）。
  `REFRESH_COST`（¥50）は**廃止し、ガチャ料に統合**（v21 からの宿題を消化）。

  | 最高解放規模 | 単発 🔧 | S期待コスト（20連） |
  |---|---|---|
  | mini | ¥5万 | ¥100万 |
  | mobile | ¥15万 | ¥300万 |
  | indie | ¥50万 | ¥1,000万 |
  | hit | ¥150万 | ¥3,000万 |
  | aaa | ¥500万 | ¥1億 |

- 根拠：固定額だと中盤以降（1作¥百万〜億）に「実質無料で回し放題」となり、REFRESH_COST
  ¥50 と同じ失敗（重みのない抽選）を繰り返す。規模連動なら、序盤は「痛いが狙える」
  （初期資金¥500万に対し S 期待¥100万）、終盤は「余った金の吸収先」（aaa で S 期待¥1億＝
  規模解放ゲートと同オーダー）として機能し、北極星の経済原則「上位規模ほどコストも
  指数的に上げて青天井を防ぐ」に整合する。最終値はシミュレーションと実プレイで調整。
- なお給与式（power×¥60万）は規模スケールしないため、終盤の実コストはガチャ料が支配的
  ＝「引く価格」がそのまま規模の重みになる。
- **雇用コストは従来どおり**（初月給即払い＋毎月給与）。S は wage 式（power×¥60万）により
  自然に高給（Lv1 で ¥72万/月）＝「金に飽かせて S を並べる」ことへの既存ブレーキが効く。
- 10連は**本版では実装しない**（§5）。

### 4-C. 天井（ピティ）🔧（叩き台・軽量案）

- **20連続で S 非排出なら次の1回を S 確定** 🔧。カウンタは S 排出でリセット。
- 目的：確率の下振れで「引く楽しみ」が「恨み」に転じるのを防ぐ（長く遊ぶ人が一番得する）。
- カウンタはセーブに永続化（§7 セーブ影響）。実装コストが小さい単純カウンタ方式のみ。
  演出上のカウント表示（「あと N 回で S 確定」）は任意 🔧。

## 5. スコープ外（本版では作らない）

- **10連ガチャ**：候補在庫UIが必要になり複雑化。単発の手応えを見てから判断（次版以降）。
- **広告連動（無料ガチャ1日1回等）**：広告SDKは v0.24 で本実装。モック広告で入れると
  「広告は人質にしない」の検証ができないため、v0.24 の広告設計に委ねる。
- **S 固有ボーナス（新規数値経路）**：§2 のとおり採用しない。
- **ガチャ限定キャラ・期間限定排出**：コンテンツ量産が必要。エンドゲームは v0.23 の主題。
- **PixelLab 新規素材の発注**：まず既存トーン（CSS＋既存ドット絵）で開封演出を成立させる。
  素材発注が必要と判断した場合はオーナー承認を取ってから（発注リストを提示）。

## 6. UX

- **場所**：OfficeScreen の採用モーダルを改修（新画面は作らない）。
- **開封演出**（カード開封・ランク開示）：
  1. 「ガチャを引く ¥{規模別価格}」ボタン → カード裏面が出現
  2. ランク色のフレーム発光（B=銅 / A=銀 / S=虹 🔧 配色は実装時に game-ui-design 規約で確定）
  3. カードめくり → 名前・役職・能力・specialty・ランクバッジ表示
  4. S のみ追加フラッシュ＋紙吹雪（既存の特大ヒット演出部品を流用）
- SE：既存SE資産の流用のみ（新規音源は v0.24 の主題）。
- 開封後に「雇用する ¥{wage}」「見送る」の2択。満席（12人）時は雇用ボタン無効化（現行踏襲）。
- 演出は**スキップ可能**（連続で引くときにテンポを殺さない。クリックで即結果）。
- 1280×720 固定内・スクロールなし（既存UI規約）。

## 7. 技術メモ

- 純粋ロジックは `src/core/gacha.ts`（仮）に置く：`rollRank(rng, pityCount)` /
  `newCandidateWithRank(rng, rank)`。`newCandidate()` は内部でレンジを受け取る形にリファクタし
  重複を作らない。rng は既存のシード注入方式を踏襲（テスト可能に）。
- 排出率・帯域・規模別価格テーブル・天井は `src/data/balance.ts` に `GACHA_CONFIG` として
  まとめ、叩き台/確定をコメントで区別（INVEST_CONFIG と同型）。価格の参照規模は
  `currentRent` と同じ「解放済み最高規模」判定を流用する。
- **セーブ影響**：ピティカウンタ（int 1個）の追加。既存の候補スロット（`Candidate`）は
  「開封済み・未雇用カード」の保持に流用可能か実装時に判断 🔧。セーブバージョンは
  現行スキーマに単純フィールド追加で済むならマイグレーション最小（デフォルト0で補完）。
- `REFRESH_COST` と関連UI（「別の候補 ¥50」）は削除。参照箇所を grep で全消し。
- テストは testing-rules 規約に従い、境界値（排出率の合計=100%・帯域境界・ピティ発火・
  満席時・資金不足時）を優先。

## 8. 判断ゲート（roadmap 原文＋本書で具体化)

1. **分布ガード維持**：`balanceSimulation.test.ts` の序盤 persona（現行「新人3人・全上振れ
   0.6」）を **S上限 0.7×3 に更新**しても「序盤 メタ70+＝0%」が維持されること。
   - 概算：mini で S×3 は powerBonus 58.8＋多様性10 ＝ charPower 68.8（現行上振れ 60.4）。
     約8pt 上がるため、**必ずシミュレーションで実測**し、破れる場合は S の帯上限を下げる
     （0.65 等）か B/A/S 帯を再調整する。天井（POWER_CAP・上限70）自体は動かさない。
2. **進行ガード維持**：`progressionSimulation.test.ts`（mobile 8〜16作・aaa 25〜60作・
   60作Lv7+）に、候補生成のランク方式＋ガチャ料支出を反映して緑を維持すること。
   平均 basePower 0.40→0.36 の低下と、ガチャ料という新規支出の両方が効く方向なので要実測。
3. **「引きの快感」の成立**はオーナー実プレイでのみ確認可能（機械検証不可・§9末尾）。
