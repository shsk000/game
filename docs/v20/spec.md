## 0. 前版からの学び（v0.19.2 変更履歴より）

> 作業感の診断「意思決定の不在」は誤り。打鍵の中に意思決定を挟むと爽快感が死ぬ。
> 作業感は打鍵の外側（v20 の投資・育成、ジュース強化）で解く

この結論を受け、v20 は**打鍵フローを一切止めない**前提で5つのパターンを順番に実装する：

| # | パターン | 状態 |
|---|---|---|
| A | ジュース強化（コンボ音階SE・コンボ称号ポップ） | ✅ 実装済み |
| A-2 | 入力に合わせたアクション増量（かな消化ポップ・進捗フライアウト・PERFECTシェイク・FEVERバナー） | ✅ 実装済み |
| B | 間欠サプライズ（クリティカル打鍵・レア文章） | 🔧 本版で計画・実装 |
| C | 自動の山場（クランチタイム・ボス文章） | 次版でスコープ |
| D | 合計値ライブ表示（積み上げの主役化） | 次版でスコープ |
| E | ギアシフト＋パーフェクトストリーク | 次版でスコープ |

追加のオーナーFB（2026-07-12）：「FEVERということはわかったが、そもそも完成までの進捗があることを理解してなかった」
→ 開発全体の進捗（doneLoC/workTarget）の可視性が低いことが判明。パターンDで対応予定（本版のスコープ外・次版）。

## 1. コンセプト

コアループ（企画→開発→デバッグ→リリース→販売）・経済設計は**変更しない**。v20 は「1文字1文字を打つ体験」の質感だけを強化する層で、既存の数値パイプライン（品質・メタスコア・売上・進捗）に**新しい加点経路を増やさない**ことを原則とする。

新しい報酬はすべて、既存の実証済み経路（FEVERゲージ／進捗 `doneLoC`／期待度 `hype` → `axisFans`）に乗せる。`AXIS_QUALITY_BONUS_CAP`（+8）や `STAT_QUALITY_BONUS_CAP`（+8）で頭打ちになる `devStats`・`funFactor` 経由の加点は**新規報酬の主経路にしない**（v0.19.1 で一度踏んだ罠。詳細は §4）。

## 2. パターン A / A-2（実装済み・概要）

- **A**: コンボ数に応じて打鍵SEの音階が半音ずつ上がる（`JUICE_CONFIG.keyPitch`）。コンボ 50/150/300 到達で称号ポップ（`JUICE_CONFIG.comboTitles`）
- **A-2**: 入力中のかな1文字（モーラ）ごとにポップ/バウンス/スパーク演出。1文字ごとの進捗フライアウト数字。PERFECT文字数達成時の画面シェイク。FEVER突入時のバナー演出
- 実装：`src/core/juice.ts`（純粋関数）・`src/features/develop/DevelopScreen.tsx`（KanaActionLine等）・`src/styles/global.css`
- 副次対応：かな進捗の表示位置がローマ字打鍵数からの近似では拗音の代替入力パターン（例：しゅ＝shu / si+ゅ）で破綻することが実プレイで判明 → `@shsk002/nano-type-jp` を 0.7.0 に更新し `resolvedUnitCount`（実値）ベースに置き換え（近似ロジック全廃）

## 3. パターン B: 間欠サプライズ（クリティカル打鍵・レア文章）

**目的**：単調な「順番に打つだけ」の中に、予測できない「当たり」の瞬間を挟み、次の一打・次の一文への期待値を作る。作業感の対義語＝「次が気になる」。

### 3-1. クリティカル打鍵

- 発生条件：**開発フェーズ**の正打（`onCorrect`）ごとに `JUICE_CONFIG.crit.rate`（2%）で発生
- 効果：FEVERゲージに通常 `+1` の代わりに `crit.feverBonus`（+12 = ゲージの20%）を一気に加算。既存の `addFever` をそのまま使うのでフィーバー本体のロジック（発動・効果・減衰）は無改修
- 演出：`sfx.crit()`（既存スタブ）＋ 打鍵位置に金色スパークのポップ（`.dev-crit-spark`、`.dev-kana-spark` のパターンを踏襲）＋軽い画面フラッシュ
- 企画フェーズでは発動しない（FEVERが開発フェーズ専用という既存の設計境界（v15確定）を踏襲。新しいゲージを増やさない＝最小変更）

### 3-2. レア文章

- 発生条件：**開発フェーズ**で次の文章を選ぶ瞬間（`pickPhrase` 呼び出し時）に `JUICE_CONFIG.rare.rate`（7%）で「レア」フラグを立てる
- 表示：文章カードに「★レア」バッジ＋文字色変更で視覚的に区別（打ち始める前から見えているので、打っている間ずっと期待感が続く）
- 報酬（**因果チェーンを確認済み**。詳細は §4）：完走時に FEVER ゲージへ `rare.feverBonus` を加算するのみ。
  `JUICE_CONFIG` 冒頭のコメント通り「報酬はすべてフィーバーに合流させる」設計に統一し、
  クリティカルと同じ経路（新しい加点チャネルを増やさない）にする。`devStats` / `funFactor` への
  直接倍率適用はしない（§4）
- 企画フェーズでは発動しない（クリティカルと同じ理由。FEVERが開発フェーズ専用という既存の設計境界を
  踏襲する。企画フェーズ向けの間欠サプライズは、hype/funFactorの扱いに新しい設計判断が要るため
  次版で改めて検討する）
- 演出：完走時、通常の結果カードに加えて「★レア達成！」ポップ（既存 `comboTitle` ポップのパターンを踏襲）

### 3-3. 数値（叩き台 🔧 → 実装時に調整）

```ts
crit: { rate: 0.02, feverBonus: 12 },
rare: { rate: 0.07, feverBonus: 20 },
```

`JUICE_CONFIG.rare` の `statMult` は撤去する（§4 の理由）。レア文章はクリティカルより発生率は低いが
1回あたりのフィーバーボーナスを大きくする（クリティカルは打鍵単位の小さな驚き、レア文章は
文章単位の大きな驚き、という粒度の違いを数値で表現）。

## 4. 報酬の因果チェーン確認（実装前チェック・v0.19.1 の再発防止）

`src/core/release.ts` を実装前に確認した結果：

- `devStats`（属性）→ `statQualityBonus` は `STAT_QUALITY_BONUS_CAP`（+8）で頭打ち。さらに `funFactor` 等と合算後 `AXIS_QUALITY_BONUS_CAP`（+8）で**二重に**頭打ちされる。通常プレイでは終盤までにこの上限へほぼ到達するため、**1文だけ devStats を3倍にしても最終品質にはほぼ届かない**（v0.19.1 で一度実際に踏んだ罠と同一構造）
- `axes.funFactor` も `devStats` と同じ `AXIS_QUALITY_BONUS_CAP` 経由のみ → 上記と同じ罠
- `JUICE_CONFIG` 冒頭のコメント（実装前から存在）が既に「報酬はすべてフィーバーに合流させる」と明記していた。当初 `rare.statMult` を `devStats` に直接適用する案はこの原則と矛盾しており、実装前チェックで撞着に気づいて修正した
- FEVER 経由の効果（進捗×2・devStats×1.5、15秒間のみ）は既存実装（v15）で、進捗×2 の部分は `doneLoC`（無上限）に直結するため、レア文章の1回のフィーバーチャージ増量は「発動しやすくなる／発動が伸びる」という形で確実に最終結果に届く

→ レア文章もクリティカルと同じく **FEVERゲージへの加点のみ**を新設し、`devStats` / `funFactor` への直接倍率適用は行わない。

## 5. パターン C〜E（次版でスコープ・本版では未着手）

- **C: 自動の山場（クランチタイム・ボス文章）** — `JUICE_CONFIG.crunch`（全体完成度80%以上で進捗×2、選択なし自動発動）が既に叩き台としてある。ボス文章（長文・高報酬）の設計は未着手
- **D: 合計値ライブ表示（積み上げの主役化）** — オーナーFB「完成までの進捗があることを理解してなかった」に直結。現状「開発全体の進捗」は左サイドバーの小さい数字のみ。中央（打鍵の視線の近く）に常時見える形での再配置が必要
- **E: ギアシフト＋パーフェクトストリーク** — `JUICE_CONFIG.gears` / `perfect` が既に叩き台としてある。入力速度(wpm)でギアが切り替わる演出、ノーミス連続文数のストリーク表示は未着手
