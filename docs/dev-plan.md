# 企画ループ（/dev-plan）設計

> 共通の土台（なぜ多エージェントか・ロール定義・4ゲート思想・人間ゲートの位置）は `docs/dev-loop.md`。
> 実装フェーズの規約は `docs/dev-build.md`。このドキュメントは **「何を・なぜ作るかを決める企画ループ」** の設計。

---

## 1. 目的

「次に何を作るべきか」を、**責任者（プロデューサー）が実際にゲームを遊んで**決め、**社長（オーナー）の承認**を得るまでの工程。最上位の目的（継続＝広告収益、`game-design`）に照らして差分を提案する。

現行の一括ループ（責任者→実装→…→PR を自動）は人間ゲートが末尾（PR）だけで、**設計の良し悪しを実装前に止められない**という失敗があった（例：正しく動くが報酬窓を画面の奥に埋めた）。企画ループはこれを、**実装の手前に社長承認ゲートを1回**置くことで防ぐ。

## 2. スコープ

- **やる**：現状分析（実プレイ＋コード）、提案の起票（軽量PRD）、社長承認の取得。
- **やらない**：コード変更・PR作成・技術詳細設計（それは `dev-build`）。責任者は**読み取り専用**。

## 3. ロールと情報源（遊ぶ主・コード従）

担当は責任者（`.claude/agents/producer.md`）1体のみ。判断は次の2情報源を統合する。

| 情報源 | 得るもの | 単独の弱点 |
|---|---|---|
| **実機プレイ（主）** | 退屈/詰まる/分かりにくい/埋もれてる＝**プロダクト勘** | コードだけ＝体験の欠落を検知できない（過去の失敗） |
| コード / spec（従） | 実現可能性・対象ファイル・因果・CAP | 遊びだけ＝既存機能を知らず的外れ |

**運用上の制約**：
- Playwright は背景サブエージェントだと詰まる（ロック掃除に権限が要る）→ **実機プレイはメインセッションで**行う。
- ゲームは時間律速 → DEV「開発を即完了」等で早送りして中盤まで到達してから評価する。
- タイムボックス：ブラウザ操作は目安20手で打ち切る（分析に溶かさない）。

## 4. 手順

1. **分析**：最上位の目的を再確認し、現ゲームを実プレイ（新規〜中盤）＋コードで裏取り。ボトルネック/ギャップを列挙。
2. **起票**：上位 `count`（既定3）件を **軽量PRD** に落とし、`docs/plans/<id>/proposal.md` に **1提案1ファイル**で書いてコミット。
3. **提示**：社長へ提案を要約提示し、判断を仰ぐ。
4. **社長ゲート**：**承認 / 修正指示（再企画）/ 却下**。承認された `<id>` だけが `dev-build` に流れる。

## 5. 出力：軽量PRD テンプレート

置き場所 `docs/plans/<id>/proposal.md`。**id ＝ `YYYYMMDD-<機能スラッグ>`（例 `20260725-daily-gacha`）**、1提案1ファイル。
PRD をベースに PR-FAQ の「体験を先に書く」規律を混ぜる。**③④が肝**（ここがあれば社長が承認前に「なぜその画面の奥？」を弾ける）。

1. **タイトル / id / 優先度 / ステータス**
2. **課題（Problem）** — 実プレイで気づいた事実。最上位の目的に対するギャップ
3. **プレイヤー体験（Job Story）** — 「プレイヤーが〈状況〉のとき、〈動機〉で、〈成果〉を得る」＝**いつ・どこで・なぜ触れるか**
4. **提案（What）＋UI導線・置き場所** — 何を、どの画面のどこに出すか
5. **なぜ今／最上位の目的リンク** — 継続・広告収益にどう効くか
6. **成功条件・指標** — 完成条件＋測れる指標
7. **スコープ外（Non-goals）**
8. **リスク／要社長判断** — 新テーマ・大投資・コアループ改変フラグ

> **ステータス**（proposal 冒頭メタに `- **ステータス**: 未完了` として持たせる。/dev-plan が起票時に付与）:
> - `未完了` … 起票済み・未着手（初期値）
> - `進行中` … /dev-build で実装中（実装〜PR）
> - `完了` … 開発ループ通過（実装・検証・審査OK・PR作成済み。マージは社長）

## 6. 社長への提示フォーマット（必須）

`proposal.md` は**実装者向け**、社長への提示文は**社長向け**。同じ内容を短くするのではなく、**翻訳する**。
過去の失敗：proposal の要約（確率・段倍率・`file.ts:123`）をそのまま貼り、「まったくよくわからない」と差し戻された（2026-07-25）。

### 必ず入れる5ブロック（この順で）

1. **実プレイの再現** — 時系列の箇条書き。「開始 → 何をした → いくら減った → 画面に何と出た」。
   **実際の金額・点数・画面文言をそのまま**書く。社長が自分で追体験できることがゴール。
2. **なぜそうなるのか** — 結果画面の内訳などを**表**で見せ、因果を1本の線で説明する。
3. **提案一覧** — 「**直すこと / 効果 / コスト**」の3列表。1提案1行。
4. **決めてほしいこと** — **1つに絞る**。選択肢を A/B/C/D で並べ、**推奨を明示**する（「現状維持」も選択肢に含める）。
5. **依存関係** — 「これを直さないと他の提案が効かない」があれば1〜2行。

### 数字は「だから何？」まで翻訳する

生の数値を置くだけでは伝わらない。**プレイヤーに起きること**に変換する。

| ❌ そのまま出す | ✅ 翻訳して出す |
|---|---|
| 両合致確率 1.19% | 当たるまで待つと**実時間で8時間半** |
| `salesMultiplierForScore` が 0.333→3.333 | **1点差で売上が10倍**変わる崖がある |
| charPower 重み 0.6、実力9点 | 点数の6割を占める社員の能力が、雇いたてだと**100点満点で9点** |
| ROI -89.4% | 1本作るごとに**約100万円の赤字**。4〜5本で破産 |

### 提示文に書かないもの（proposal.md 側に置く）

- `file.ts:123` 形式の行番号・関数名・変数名・定数名
- 内部用語（CAP／段倍率／分布ガード／ツァイガルニク／§10-② のような節番号引用）→ **日常語に置き換える**
- 取り下げ・重複整理・コミットハッシュ等の**進行管理の話** → 最後に1〜2行だけ
- 提案を却下/取り下げた経緯の詳細 → `proposal.md` に書けば足りる

### 分量と自己チェック

- 分量の目安：**表3つ＋箇条書き中心**。長い段落を積まない。
- 提示前に1回だけ自問する：
  - [ ] このゲームを知らない人が読んで、**何が問題か／いくら損しているか／何を決めればいいか**が分かるか
  - [ ] 出した数字はすべて「だから何？」に答えているか
  - [ ] **決めることが2つ以上になっていないか**（増えたら提案を分割する）

## 7. 社長承認ゲート

- **承認**：`<id>` を `dev-build` へ。複数承認可。
- **修正指示**：論点を添えて企画ループへ差し戻し（再プレイ／再起票）。
- **却下**：`proposal.md` に却下理由を残して打ち切り。
- **要社長判断（🔧）が付いた提案**（バランス改変・新テーマ・大投資）は、承認時に方針まで社長が明示する。

## 8. 次工程へのハンドオフ

承認された `docs/plans/<id>/proposal.md` を入力に、`dev-build`（開発ループ）が同じ `<id>` ディレクトリへ技術計画 `plan.md` を足して実装する。詳細は `docs/dev-build.md`。
