# docs/ のドキュメント運用規約

このディレクトリで設計・タスクを扱うときに Claude（あなた）が守るべきルール。

> `docs/vNN/`（版ごとの企画書）は**全廃した**。
> 理由：`vNN/spec.md` は「その版を計画した時点の決定」で、その後の開発で実装と食い違い、
> それを現行仕様として読んだことによる事故が繰り返し起きた（詳細はリポジトリ直下の `CLAUDE.md`）。
> 旧 `vNN/` の内容は git 履歴に残っている（`git log --diff-filter=D -- docs/v14/spec.md`）。

---

## 1. ディレクトリ構造

```
docs/
  CLAUDE.md           ← このファイル（docs の運用規約）
  spec/               ← ★現行の確定仕様（生きた資料）。実装と一致させる
    CLAUDE.md         ← spec を書くときのルール（このフォルダで作業すると自動で読まれる）
    glossary.md       ← 用語定義（何がどこに属するか・どの機能が実際に効いているか）
    scoring.md        ← 品質・メタスコア・売上の計算式
  plans/<id>/         ← 検討中の提案と決定履歴
    proposal.md
  roadmap.md          ← これから作るものの地図
  architecture.md     ← コード構造の設計判断（logic-architecture スキルの詳細版）
  testing.md          ← テスト戦略の詳細（testing-rules スキルの詳細版）
  qa/                 ← バグハント手順・ユースケース
```

**現行仕様を書く場所は `docs/spec/` だけ。** ここ以外を「今どうなっているか」の根拠にしない。

---

## 2. 3つの置き場の使い分け

| 置き場所 | 役割 | 更新 |
|---|---|---|
| **`docs/spec/`** | **現行の確定仕様** | **ロジックを変えたら同じコミットで更新（必須）** |
| **`docs/plans/<id>/`** | 検討中の提案・未確定（🔧）・決定履歴 | 検討中のみ。決定したら `spec/` に反映し、proposal は履歴として残す |
| `docs/roadmap.md` | これから作るものの地図 | 随時 |

`plans` の id は `YYYYMMDD-<英語スラッグ>`（例 `20260725-score-redesign`）。日付は起票日。

---

## 3. docs/plans/<id>/proposal.md の書き方

### 必須要素
- **目的をオーナーの言葉で1行**
- **課題（Problem）** — 実コードの `file:line` を根拠に書く。憶測で書かない
- **提案（What）** — 未確定の分岐は 🔧 を付けて選択肢を並べる
- **完成条件（検証チェックリスト）** — ユーザー操作の言葉で書く（dev-flow ゲート[3]の消し込みリストになる）
- **スコープ外（Non-goals）**
- **決定履歴** — オーナー判断が出たら日付付きで追記する

先頭にステータスを書く：`計画（GO待ち）` / `実装中` / `実装完了・検証済み` / `不採用`

---

## 4. Claude（あなた）の動き方

### 設計・仕様に関する質問を受けた時
1. **`docs/spec/glossary.md` を最初に読む** → 該当する章へ
2. `docs/spec/` に無いことは**コードを読んで確認する**。憶測で答えない
3. 過去の経緯が必要なときだけ `docs/plans/` と git 履歴を見る

### 仕様変更を依頼された時
1. 影響範囲を判定する
2. **`docs/plans/<id>/proposal.md` に起票**し、未確定点は 🔧 で残してオーナーのGOを待つ
   （dev-flow ゲート[1]。GO なしで実装を始めない）
3. 実装したら **`docs/spec/` を同じコミットで更新**する

---

## 5. リンク・参照

- コード中のコメントから仕様を参照するときは **`docs/spec/` を指す**（消える資料を指さない）
- `docs/plans/` から `docs/spec/` へのリンクは可。逆（spec から plans）は原則書かない

---

## 6. このファイル自体の更新

規約変更は **明示的な相談の上で**。勝手にルールを変えない。
