# lessons.md — 指摘から学んだ再発防止ルール

## 2026-07-10（テスト基盤導入〜v16計画のセッション）

1. **「計画して」と言われたら、実装は明示の GO が出るまで一切始めない**
   - 事象：v16 の計画指示中にテスト基盤の実装（承認済み）を続けていたら「計画しろと言っただけ、なんで開始してるの？」と受け取られた
   - ルール：計画フェーズと実装フェーズが並走するときは、**今どちらの作業をしているかを毎回明示**する。新規テーマは計画→レビュー→GO→実装を厳守

2. **設計資料には「何をどう考えたか」を書く（結論の羅列は資料ではない）**
   - 事象：「完全ヘキサゴナルはやり過ぎ」程度の理由付けで出したら「考えが一切ない」と指摘された
   - ルール：設計資料は必ず ①最適化したいゴール（このプロジェクト固有の前提） ②比較した選択肢と落選理由 ③個別判断の理由、を含める

3. **テーマの違う資料・スキルは分割する**
   - 事象：アーキテクチャとテスト規約を1つのスキルにまとめて「分けるべき」と指摘された
   - ルール：参照タイミングが違うもの（コードを書くとき／テストを書くとき）は別ファイルにする

4. **作業開始前にブランチ/worktree を確認する**
   - 事象：main チェックアウト上で作業を始めてしまい、worktree への移設と main の掃除が発生した
   - ルール：セッション開始時に `git branch --show-current` と worktree 運用の有無を確認してから着手

5. **削除系コマンドが権限拒否されたら、ユーザーに実行してもらうコマンドを提示する**
   - 事象：main 側の掃除で rm が拒否 →「rm したいならコマンド発行して。こっちで削除します」
   - ルール：拒否されたら再試行せず、コピペ可能なコマンドとして提示する

## 2026-07-11（「さっきから自分でちゃんとテストしてる？」）

6. **ゲームプレイに関わる変更は「本物の入力経路」で検証する**
   - 事象：バグ発生システムを store アクション直呼びと unit テストだけで検証し、
     「コンボ切れ時しかミス判定されない」欠陥や体感のズレ（76%で3匹）を見逃した
   - 合成 KeyboardEvent の自動プレイドライバは React の描画と desync して信頼できない
   - ルール：入力起点の機能は **Vitest Browser Mode の実CDP入力テスト**（userEvent.keyboard）で
     入力経路全体（キーボード→hook→store）を固定する。体感の最終確認はオーナーの実プレイ

## 2026-07-11（v19選択制の迷走と「検証してなさすぎ」）

7. **開発は4ゲート（計画→実装→検証→レビュー依頼）を必ず順番に通す** → `.claude/skills/dev-flow` に成文化
   - 事象①：チャレンジ報酬を品質上限(+8)で無効化される経路に乗せて「作ったけど反映されてない」
     → 計画時に効果の因果チェーンを最終結果まで追っていなかった
   - 事象②：store 直呼びのショートカットで流れを見ただけで「実機検証済み」と報告 →「自分検証してないけど？」
   - 事象③：unit/ui が緑の時点でレビュー依頼し e2e を回し忘れ →「検証は？」
   - ルール：レビュー依頼は検証（4点セット＋Playwright実機で本物の入力＋計画の完成条件の実測消し込み）が
     **全部終わってから**。機械で確認できない体感項目は「オーナー確認待ち」と明示ラベル

8. **対症療法を2回重ねたら手を止めて目的に立ち返る**
   - 事象：選択制への不満に自動通過→報酬付替えと対症を重ね、3度目の指摘でようやく
     「打鍵を止める構造自体が誤り」という根本原因に到達（結論：完全撤回）
   - ルール：同じ趣旨の指摘が2回来たら、修正案を出す前に「そもそもの目的は何か」を1行で書き直して
     手段ごと疑う

## 2026-07-25〜27（スコアモデル0から再設計のセッション）

9. **選択肢への回答を実装GOと誤読しない**
   - 事象：提示した案への回答「50%+大きすぎる」を受けて GO なしで実装に着手し、
     「売上の式を聞いただけなのに何が完了したの」となった
   - ルール：オーナーの発言が「質問への回答」か「実装開始の指示」かを区別する。GO は明示の言葉だけ

10. **用語は 定義→合意→用語集記載→使用 の順**（game-design スキルに成文化済み）
    - 事象：「伸びる量」「打鍵の質」「段倍率」等を思いつきで使い、「何の話をしているのか
      わからない」を同一セッション内で繰り返した

11. **決めていないことを決まったように資料へ書かない**
    - 事象：「職種とスキルは1対1」「社員は5スキル全部持つ」を勝手に前提化して資料に書き、
      2度指摘された。オーナーの発言から一般化しない。例示の表で暗黙の前提を作らない

12. **AI向けのルールは自動で読み込まれる場所に置く**（README では挙動を制御できない）
    - 置き場：リポジトリ直下 CLAUDE.md／docs/CLAUDE.md／対象ディレクトリの CLAUDE.md／スキル

13. **前提が変わったら結論を再計算する**
    - 事象：モデル切替後の再分析で「対策の根拠数字の誤り」「決定済み Q1-A の実装漏れ」を発見。
      過去の自分の結論を信用しない

14. **spec と plan の突き合わせを怠らない**
    - 事象：「planに全部入ってる？少ない気がする」の指摘で、plan の漏れ6件・spec の穴4件
      （相性の効き先が式に無い等）が見つかった。資料を書いたら双方向で照合する

15. **スケールの違う2つの値を「変換」でつながない。切り替えは一点に集約する**
    - 事象：実装ステップ1 で「総合力 ÷ 100 → 旧 power」の互換アダプタを入れたが、
      旧 power 帯（B 0.2〜0.4）と新しい総合力帯（Lv1 15〜28）は単位が違い変換にならない。
      採用社員の平均能力が半減し、序盤の総売上が10分の1になった
    - ルール：新旧の値をつなぐ前に**両方の帯（min/max）を並べて書く**。単位が合わないなら
      アダプタを作らず「旧ロジックを凍結して並走させ、切り替えは1コミットで一度に」

16. **ガードは本番が実際に呼ぶ入口から通す。「同じ入力なら同じ出力」は恒真になりやすい**
    - 事象：安全弁として置いた「power が同じならスコアが同じ」は、アダプタが何をしても通る
      恒真テストだった。463件全緑のまま −90% の売上回帰が通過した
    - さらに、書き直した分布テストもランクを自分で決めて渡していたため、本番が呼ぶ
      ランク抽選関数を一度も通らず、C を 35% 排出するバグを**2度目も**素通しした
    - ルール：ガードは `store.action()` のような**本番の入口**から入る。ヘルパを直接叩くテストは
      式の検証にしかならない

17. **ガードは「落ちるところを一度実際に見る」まで信用しない**
    - 事象：上記のとおり、本番が通らない経路にガードを置くミスを連続で2回やった
    - ルール：回帰を防ぐテストを書いたら、**バグを一時的に再現してテストが落ちることを確認**し、
      その実測値をコミットメッセージに残す（例：バグ再現時 平均メタ 27.795 で落ちる）
