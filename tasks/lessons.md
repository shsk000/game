# lessons.md — 指摘から学んだ再発防止ルール

## 2026-07-10（テスト基盤導入〜v16計画のセッション）

1. **「計画して」と言われたら、実装は明示の GO が出るまで一切始めない**
   - 事象：v16 の計画指示中にテスト基盤の実装（承認済み）を続けていたら「計画しろと言っただけ、なんで開始してるの？」と受け取られた
   - ルール：計画フェーズと実装フェーズが並走するときは、**今どちらの作業をしているかを毎回明示**する。新規テーマは計画→レビュー→GO→実装を厳守

2. **設計資料には「何をどう考えたか」を書く（結論の羅列は資料ではない）**
   - 事象：「完全ヘキサゴナルはやり過ぎ」程度の理由付けで出したら「考えが一切ない」と指摘された
   - ルール：設計資料は必ず ①最適化したいゴール（このプロジェクト固有の前提） ②比較した選択肢と落選理由 ③個別判断の理由、を含める

3. **テーマの違う資料・スキルは分割する**
   - 事象：アーキテクチャとテスト規約を1つのスキルにまとめて「分けるべき」と指摘された
   - ルール：参照タイミングが違うもの（コードを書くとき／テストを書くとき）は別ファイルにする

4. **作業開始前にブランチ/worktree を確認する**
   - 事象：main チェックアウト上で作業を始めてしまい、worktree への移設と main の掃除が発生した
   - ルール：セッション開始時に `git branch --show-current` と worktree 運用の有無を確認してから着手

5. **削除系コマンドが権限拒否されたら、ユーザーに実行してもらうコマンドを提示する**
   - 事象：main 側の掃除で rm が拒否 →「rm したいならコマンド発行して。こっちで削除します」
   - ルール：拒否されたら再試行せず、コピペ可能なコマンドとして提示する

## 2026-07-11（「さっきから自分でちゃんとテストしてる？」）

6. **ゲームプレイに関わる変更は「本物の入力経路」で検証する**
   - 事象：バグ発生システムを store アクション直呼びと unit テストだけで検証し、
     「コンボ切れ時しかミス判定されない」欠陥や体感のズレ（76%で3匹）を見逃した
   - 合成 KeyboardEvent の自動プレイドライバは React の描画と desync して信頼できない
   - ルール：入力起点の機能は **Vitest Browser Mode の実CDP入力テスト**（userEvent.keyboard）で
     入力経路全体（キーボード→hook→store）を固定する。体感の最終確認はオーナーの実プレイ
