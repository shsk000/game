# /dev-plan — 企画ループ

設計は `docs/dev-plan.md`。「何を・なぜ作るか」を決めて社長承認を得るまでの工程。
**Workflow ではなくメインセッションで踏む手順**（責任者の実プレイはメインセッション必須。背景エージェントは Playwright のロック掃除で詰まる）。

## 引数（`$ARGUMENTS` を解釈）
- `count`（既定 3）: 提案件数
- `focus`（任意）: 分析焦点（例 `経済バランス`）

## 手順（責任者としてメインセッションで実行）

1. **憲章**：Skill(game-design) を読み、最上位の目的（継続＝広告収益）とロール定義を採用（再発明しない）。
2. **現状分析＝実プレイ主・コード従**：
   - dev server を起動し、接続済み Playwright MCP(`mcp__playwright__browser_*`) で現ゲームを**新規〜中盤まで実際に遊ぶ**（DEV「開発を即完了」等で早送り）。退屈／詰まる／分かりにくい／埋もれてる を拾う。**ブラウザ操作は目安20手でタイムボックス**（分析に溶かさない）。
   - `docs/roadmap.md`・最大版 `docs/vNN/spec.md`・実コード(`src/core`, `src/data`)で裏取り（実現可能性・対象ファイル・因果・CAP）。
3. **起票**：最上位の目的に対する差分を優先度付けし、上位 `count` 件を**軽量PRD**（`docs/dev-plan.md` §5 テンプレ）で `docs/plans/<id>/proposal.md` に**1提案1ファイル**で書く。id＝`YYYYMMDD-<機能スラッグ>`。
   - **③プレイヤー体験（いつ・どこで・なぜ触れるか）と ④UI導線・置き場所を必ず埋める**（ここが弱いと社長が承認前に弾けない）。
   - コードは変更しない。`git add docs/plans/<id>` で proposal をコミット。
4. **社長ゲート**：提案を要約提示し **承認 / 修正指示 / 却下** を仰ぐ。

## 実行後にやること
- **承認**された id を `/dev-build ids=<id>,<id>` に渡す（開発ループへ）。
- **修正指示**なら論点を受けて再プレイ／再起票。**却下**なら proposal.md に却下理由を残す。
- **要社長判断（🔧）付き**の提案（バランス改変・新テーマ・大投資）は、承認時に方針まで社長に明示してもらう。
