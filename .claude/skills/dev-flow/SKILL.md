# 開発フロー（計画→実装→検証→レビュー依頼）

**4つのゲートを順番に通す。ゲートを飛ばした瞬間に事故が起きる**（下部のアンチパターン集はすべて実際に起きた）。
レビュー依頼はフローの最後。**検証がすべて終わって「完全に完成」してから**しか出せない。

```
[1] 計画 ──→ [2] 実装 ──→ [3] 検証 ──→ [4] レビュー依頼
     ↑                        │
     └── 検証で計画の誤りが見つかったら計画に戻る（実装を続けない）
```

---

## [1] 計画

**書くもの**（規模により docs/vNN/spec.md か、会話内の計画提示。docs/CLAUDE.md の規約準拠）：

1. **目的をオーナーの言葉で1行**書く。手段ではなく目的（例：「作業感をなくす」が目的、「選択制」は手段）。
   途中で手段に迷ったら必ずこの1行に立ち返る
2. **効果の因果チェーンを既存コードで末端まで追う**。新しい報酬・数値・効果が
   「最終結果（品質・メタスコア・売上・進捗）に本当に届くか」を実装前にコードで確認する。
   途中に**上限（CAP）・重み・クランプ・既存ガード**があれば列挙し、衝突しないことを確かめる
   - 実例：チャレンジ報酬を devStats に乗せたが `AXIS_QUALITY_BONUS_CAP`(+8) に埋もれて
     最終スコアにほぼ届かず「作ったけど何も反映されてない」になった
3. **完成条件（検証チェックリスト）を計画時に列挙する**。「何がどう動いたら完成か」を
   ユーザー操作の言葉で書く（例：「ミスなく50打すると称号ポップが出る」）。
   これが [3] 検証の消し込みリストになる。書けない計画は曖昧なので書き直す
4. 新テーマは **計画→オーナーレビュー→明示GO→実装** のゲート厳守（lessons.md #1）

## [2] 実装

- logic-architecture スキル準拠：ロジックは `core/` の純粋関数・rng/clock は注入
- testing-rules スキル準拠：ロジックを書いたら unit テスト必須（境界値優先）
- 最小変更。計画にない機能を勝手に足さない
- 実装中に計画の前提が崩れたら**手を止めて計画に戻る**（作り切ってから報告しない）

## [3] 検証 — レビュー依頼前に全項目必須

**すべて自分でやる。1つでも欠けたまま [4] に進むことを禁止する。**

### 3-1. 検証4点セット（全部緑になるまで直す）

```
npm run build      # tsc + vite
npm run test:unit  # ロジック
npm run test:ui    # 実CDP入力のユースケース
npm run test:e2e   # ジャーニー
```

4つ**全部**回す。「unit と ui は通ったから」で e2e を省略しない（実際に忘れて指摘された）。

### 3-2. Playwright MCP で実機を「実際に触る」（playwright-verify スキル併用）

- ブラウザで開き、**本物の入力**で確認する：タイピング機能なら `browser_press_key` で
  実際にキーを打つ。ボタンなら実際にクリックする
- **store のショートカット（`advancePhase()` 等の console 直呼び）は
  「状態のセットアップ」にのみ使用可。機能そのものの確認に使ったら検証と呼ばない**
  （実例：ショートカットだけで「検証済み」と報告して「自分検証してないけど？」になった）
- 数値効果は **before/after を実測**する（進捗が×1.5になる → 実際に打って増分を比べる）
- スクリーンショットを撮り、1280×720 内・スクロールなし・表示崩れなしを目視する

### 3-3. 計画の完成条件を1項目ずつ消し込む

[1]-3 で書いたチェックリストを、実機操作の実測で1つずつ潰す。
「テストが通った」はチェックリストの消し込みではない。

### 3-4. 機械で確認できない項目の扱い

音の心地よさ・体感・面白さなど自分で確認不可能な項目は、**「オーナー確認待ち」と明示的にラベル**して
レビュー依頼に含める。ラベルなしで「完了」に混ぜない。

## [4] レビュー依頼

[3] が全部終わって初めて出せる。報告フォーマット：

1. **作ったもの**（計画の目的に対して何をしたか）
2. **検証で実際に確認したこと**（実測値・スクショ・4点セットの結果。「〜のはず」禁止）
3. **オーナーにしか確認できないこと**（体感項目。確認してほしい観点を具体的に）
4. **保留・未完のもの**（あれば明示。隠して「完了」と言わない）

- テストが失敗している・検証が部分的・実装が途中 → レビュー依頼せず、状態を正直に報告する
- 「完了」「対応しました」は 3-1〜3-3 が全部済んだときだけ使う

## フロー自体の自己改善ルール（オーナー指示 2026-07-11）

**開発フローの運用にオーナーから指摘が入ったら、その場でこのスキルを積極的に更新して品質を保つ。**

1. フローに関する指摘（検証の抜け・報告の仕方・手順の欠陥・新しいルール）を受けたら、
   **同じセッション内で** SKILL.md に反映する。「次から気をつける」で済ませない
2. 具体的な失敗があった場合は下のアンチパターン集に**実例として1行追記**する
   （抽象的な教訓より、起きたことそのままの方が再発防止に効く）
3. `tasks/lessons.md` にも同じ教訓を記録し、スキルの変更はコミットに含める
4. 指摘が既存ルールと矛盾する場合は、勝手に上書きせずオーナーにどちらを取るか確認する

## アンチパターン集（このプロジェクトで実際に起きた失敗）

| # | 失敗 | 破ったゲート |
|---|---|---|
| 1 | チャレンジ報酬を上限+8で無効化される経路に乗せ、「作ったけど何も反映されてない」 | [1]-2 因果チェーン未確認 |
| 2 | console から store 直呼びで流れを見ただけで「実機検証済み」と報告 | [3]-2 本物の入力でない |
| 3 | 自分で触らずに「残るはオーナー実プレイのみ」と完了報告 | [3] を丸ごとオーナーに転嫁 |
| 4 | unit / ui が緑になった時点でレビュー依頼し、e2e を回し忘れ | [3]-1 の4点目を省略 |
| 5 | 「毎回選択で打鍵が止まる」体験の欠陥をテスト緑だけで見逃し | [3]-3 完成条件を操作の言葉で書いていない |
| 6 | 対症療法（自動通過・報酬付替え）を2回重ねてから根本原因に気づく | [1]-1 目的への立ち返り不足 |
| 7 | 提示した選択肢への回答（「50%大きすぎる」）を実装GOと誤読して着手 | [1]-4 明示GOの確認 |
